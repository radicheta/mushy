## Summary

`pid_derivative_filter_tau: 10.0` is declared in `fc_config.yaml` and read into the
parameter table at `fc_controller.py:42`, but it is **never passed to the PID, nor used
anywhere in the controller or in the vendored `simple_pid/pid.py`**. Confirmed by grep
across the entire `src/chambers/fc-core/` tree: only references are the param
declaration line, the YAML default, and a `test_controller.py` assertion that the
param exists. The vendored library is `simple_pid v2.0.0` (per the header comment) and
its `__call__` computes `_derivative = -Kd * d_input / dt` with no filter; **upstream
`master` on github.com/m-lundberg/simple-pid is identical** — there is no derivative
filter to "turn on", filtering must be added by the integrator (us).

Since Phase 27 shipped, Kd=4.0 has been multiplying raw, single-tick sensor jitter at
the 5Hz controller cadence directly into duty. The farmer's 2026-05-04 calibration log
(`docs/pid_calibration_notes.md`) explicitly observes this on the dashboard:
*"orange duty trace shows clear tick-to-tick jitter (~±5–8 % swings) ... unfiltered-
derivative noise made visible — the bug is observable on the live dashboard."*

**Primary recommendation:** **Option (a)** — add a first-order IIR low-pass on the
derivative term inside `fc_controller.py`, computed against the same `(input, dt)` the
PID sees, leaving the vendored library untouched. ~15-20 lines including reset
hooks for mode-C exit and (future) heater-cycle discontinuities. Set `Kd=0`
on the underlying PID and inject the filtered D contribution into the output sum,
*or* override `_pid._derivative` after the call (cleaner: see code-shape sketch
below). This preserves the "Do NOT modify" comment on the vendored file (line 24)
and makes the filter testable in isolation.

### Pattern 1: First-order discrete IIR low-pass

**What:** discrete equivalent of `H(s) = 1/(1 + τ·s)`. Standard form:

```
α = dt / (τ + dt)        # exponential smoothing coefficient
y[n] = α · x[n] + (1 - α) · y[n-1]
```

For τ=10s, dt=0.2s (5Hz tick): α = 0.2 / 10.2 ≈ **0.0196** → each sample contributes
~2% of the new value, 98% retained from history. Effective averaging window ≈ 5τ ≈
50 samples (10s).

**When to use:** noise rejection on the derivative path, where the noise is
high-frequency (per-tick jitter) and the signal of interest (real RH transients) is
low-frequency (chamber τ ≈ 600s plant time constant; door-open events ≥ 5s).

**Step response:** 63% in τ, 95% in 3τ, 99% in 5τ. With τ=10s: D term reaches 63% of
step amplitude in 10s, 95% in 30s. Meets the FILT-03 "responds within 10-20 s" bound
*at the 63% level*; for "fully responds" the bound is closer to 30s. Document this
honestly.

**Source:** [CITED: controlguru.com "Using Signal Filters In Our PID Loop"], [CITED: Åström & Hägglund, *PID Controllers* 2nd ed, Ch.6 — derivative filtering with N=Td/Tf]

### Pattern 2: dt-aware coefficient

**Critical:** because `control_interval=1.0` but actual `dt` is computed from the wall
clock (line 408-412), `dt` may vary tick-to-tick (especially after sensor staleness
recovery, mode-C transitions, or scheduler hiccups). **Re-compute α each tick from the
current `dt`** — do not pre-cache. This is the same principle the simple_pid library
uses for its own dt handling at line 169-173.

```python
def _filter_coeff(tau: float, dt: float) -> float:
    """α for the discrete first-order IIR. Returns 1.0 if τ <= 0 (filter disabled)."""
    if tau <= 0.0:
        return 1.0
    return dt / (tau + dt)
```

`tau <= 0.0` is the "disabled" sentinel — useful for A/B testing (set `tau=0` via
`ros2 param set` to bypass the filter live).

### Pattern 3: Reset on discontinuity

**What:** when the controller transitions across a mode boundary that breaks
derivative continuity (Mode C entry/exit, bumpless transfer, sensor staleness
recovery, future heater-cycle recovery from 999.34), the filter state from the prior
mode is **stale and must not propagate**. Three options, pick per-event:

1. **Hold zero** (`d_filtered = 0`, `last_input = current_input`): treat as a fresh
   start. Use after bumpless transfer / Mode C exit / staleness recovery — the prior
   D contribution shouldn't influence the post-transition tick.
2. **Hold previous** (no change to `d_filtered`, but skip update on this tick): use
   for one-tick glitches where you want to preserve momentum but not poison the
   filter. *Probably not needed for 999.32 — listed for completeness.*
3. **Reseed from current input** (`d_filtered = 0`, `last_input = current_input`,
   skip D contribution this tick): identical to option 1 in practice for our case.

**Recommendation:** option 1 (`reset_filter()` helper called from
`_engage_pid_bumplessly`, on Mode C entry, on staleness recovery — same call sites
that already manage `_pid.set_auto_mode`).

### Anti-Patterns to Avoid

- **Filtering the input (RH) instead of the derivative.** The median-of-5 buffer at
  `_humidity_buffer` (line 134) already does input-side smoothing. Adding more input
  filtering hurts P term responsiveness without targeting the actual problem (D-term
  noise). Only the D path needs the LPF.
- **Caching α across ticks.** Variable dt (after Mode-C exit, after staleness, on
  scheduler jitter) means α must recompute every tick.
- **Using a global / module-level filter state.** Filter state belongs on the node
  instance (alongside `_pid`, `_last_tick_ts`, `_effective_setpoint`).
- **Modifying `vendor/simple_pid/pid.py`.** Line 24 explicit contract: *"Do NOT modify
  — upstream is the source of truth."* If this phase ever wants to do that, it must
  first relocate or fork the vendored copy with a name change, NOT edit in place.
- **Filtering the D term *output* (post-Kd-multiplication) instead of dRH/dt.**
  Mathematically equivalent only if Kd is constant within the filter's memory window.
  Since Kd is live-reloaded, filtering pre-Kd (i.e. on dRH/dt) is more correct under
  parameter changes. **Filter the rate, not the contribution.**

reload. Adding a derivative filter is *another item in the same pattern*. Don't
reach for a new abstraction.

## Common Pitfalls

### Pitfall 1: Double-counting derivative

**What goes wrong:** if you keep `Kd=4.0` on the simple_pid library AND add an
external filtered D-term, you get 2× the derivative contribution.

**Why it happens:** intuitive "I'm just adding a filter" framing — but the lib is
already computing an unfiltered D internally. Adding without subtracting doubles up.

**How to avoid:** **set `Kd=0` on the simple_pid instance**, compute filtered D
externally, add to the lib's output before publishing. Live-reload still happens —
but on a controller-level `self._kd_effective` attribute, not on `self._pid.Kd`.

**Warning signs:** double the D contribution magnitude vs current; oscillation
worsens instead of improves.

### Pitfall 2: Filter wind-up on sensor staleness

**What goes wrong:** if sensor data goes stale for 30s (current
`sensor_stale_timeout=10`, but real DERP-relay drops can be longer), the filter
either (a) freezes (no updates, dt undefined) or (b) sees a giant `d_input` jump on
recovery (input went 94.0 → 94.0 → ... → 96.5 because chamber moved during outage)
and injects a large bogus D contribution.

**How to avoid:** call `_reset_d_filter()` whenever exiting the staleness branch
(line 401-404 transition `_safe_state_active = False`). Identical to the existing
`_disengage_pid` / `_engage_pid_bumplessly` pattern.

**Warning signs:** large negative or positive duty spike on first tick after
recovery from sensor staleness.

### Pitfall 3: dt = 0 or near-zero on first tick

**What goes wrong:** `_last_tick_ts is None` on first tick → existing code at line
409-412 falls back to `dt = 1.0`. This is fine for the filter as long as we use the
same dt the PID sees. **Don't compute a separate dt for the filter.**

**How to avoid:** pass the same `dt` value to both `self._pid(error_pct, dt=dt)` and
the filter update.

### Pitfall 4: τ < dt

**What goes wrong:** if `pid_derivative_filter_tau` is set lower than `dt` (e.g.
τ=0.1, dt=1.0), then α = 1.0/1.1 = 0.909 → filter is nearly transparent.
Mathematically fine but defeats the purpose; user may be confused why filtering
isn't working.

**How to avoid:** document the "τ should be ≥ several ticks" guidance in the param
comment in `fc_config.yaml`. **Do not enforce a floor in code** — let live-tuning
explore freely; just set the YAML default sensibly (10.0s is fine).

### Pitfall 5: Quadrature integrator cycle masquerading as derivative noise

**What goes wrong:** the 28-min I-loop limit cycle observed 2026-05-04 afternoon
(`pid_calibration_notes.md` lines 152-185) is **not** derivative noise; it's
integrator-driven. Filtering D won't kill it. **Do not claim FILT-02 success from
afternoon-session telemetry without checking the period of any residual cycle** —
short-period (≤2 min) ringing is the D-noise target; ≥10 min cycles are I-loop and
need separate Ki adjustment (already shipped per commit `184571e`).

**How to avoid:** acceptance test must pump *high-frequency* synthetic noise
specifically; or measure noise reduction on a quiet operating point where the I-loop
isn't excited.

### Pitfall 6: Frequency-domain target vs time-domain spec mismatch

**What goes wrong:** "≥3× noise reduction" can mean RMS, peak-to-peak, or spectral
density depending on noise color. Sensor jitter (~white at 5Hz tick) and a τ=10s
filter give ~50× attenuation in spectral density at Nyquist (2.5Hz), but RMS
reduction is closer to √(filter_BW / signal_BW) ≈ √(0.016 / 2.5) ≈ 12×. Both
comfortably exceed 3×.

**How to avoid:** specify the metric in the test. Recommend tick-to-tick `pid_output`
absolute-difference RMS over a 60-sample steady-state window, current vs filtered.

## Code Examples

### Code-shape sketch: option (a) integration in `fc_controller.py`

> **Not committed code.** Sketch for the planner. Sized ~20 lines net + ~15 lines test.

```python
# In __init__, after self._pid construction (~line 161):

# Phase 999.32: derivative-filter state (FILT-01..06).
# Vendored simple_pid has no D filter (file header forbids modification),
# so we compute filtered D externally with Kd=0 on the lib instance.
self._kd_effective = self.get_parameter('pid_kd').value
self._pid.Kd = 0.0   # disable lib's internal D — we own it now
self._d_filtered = 0.0
self._last_input_for_d = None
```

```python
# New helper methods on the node:

def _reset_d_filter(self) -> None:
    """Discontinuity reset — call on bumpless engage, Mode C exit, staleness recovery."""
    self._d_filtered = 0.0
    self._last_input_for_d = None

def _filtered_derivative_contribution(self, current_input: float, dt: float) -> float:
    """Filtered D term: -Kd · LPF(d_input/dt). Returns the contribution to add to PID output.

    Returns 0.0 on the first tick (no prior input to differentiate against).
    Live-reloads kd_effective and tau every call.
    """
    self._kd_effective = self.get_parameter('pid_kd').value
    tau = self.get_parameter('pid_derivative_filter_tau').value

    if self._last_input_for_d is None or dt <= 0.0:
        self._last_input_for_d = current_input
        return 0.0

    raw_rate = (current_input - self._last_input_for_d) / dt   # %RH per s
    self._last_input_for_d = current_input

    alpha = 1.0 if tau <= 0.0 else dt / (tau + dt)
    self._d_filtered = alpha * raw_rate + (1.0 - alpha) * self._d_filtered

    # D-on-measurement: contribution is -Kd · d_filtered (sign matches simple_pid line 171)
    return -self._kd_effective * self._d_filtered
```

```python
# In control_loop, after self._pid(...) call (~line 438), before publishing:

raw_pid_output = self._pid(error_pct, dt=dt)         # P + I only now (Kd=0 on lib)
d_contribution = self._filtered_derivative_contribution(error_pct, dt)
combined = raw_pid_output + d_contribution
duty = max(0.0, min(1.0, combined))                  # final clamp

# (Mode C branch unchanged: still forces duty=1.0 and resets filter)
```

```python
# Reset call sites (one line added each):

def _engage_pid_bumplessly(self):
    self._pid.set_auto_mode(True, last_output=0.15)
    self._pid_engaged = True
    self._reset_d_filter()                            # NEW
    self.get_logger().info('PID engaged with bumpless preload: duty=0.15')

# In control_loop, on Mode C entry (line 430-433):

    if self._pid.auto_mode:
        self._pid.set_auto_mode(False)

# In control_loop, on staleness recovery (line 401-404):

    self._safe_state_active = False

```

**Note on `error_pct` vs `current_humidity`:** simple_pid with
`differential_on_measurement=True` differentiates `input` (the raw measurement),
*not* error. Above sketch differentiates `error_pct` for symmetry with what the lib
*was* doing (since setpoint changes via ramp are slow, the difference is small). If
strict equivalence to D-on-measurement is desired, swap to differentiating
`self.current_humidity * 100.0` instead of `error_pct`. **Recommendation: use
`error_pct` initially** — simpler invariant that the filter's input matches the PID's
input — and revisit if calibration shows setpoint-ramp-induced D kick.

## τ Selection

### Textbook guidance

Åström & Hägglund (*PID Controllers*, 2nd ed., Ch.6) recommend the filter time
constant `Tf = Td / N` with **N typically in [2, 20], common choice N = 10**.
[CITED: Åström & Hägglund book, multiple secondary sources]

For our config:
- `Td = Kd / Kp = 4.0 / 0.35 = 11.4 s` (with current 2026-05-04 Kp=0.35)
- N=10 → Tf ≈ 1.14 s
- N=2  → Tf ≈ 5.7 s

The configured `pid_derivative_filter_tau = 10.0 s` corresponds to **N ≈ 1.14** — much
heavier filtering than textbook would suggest.

### Why heavier filtering is defensible here

1. **Plant is dead-time-dominated.** θ ≈ 50 s (per `pid_calibration_notes.md`
   2026-05-04 system-ID). Filter delay of ~30 s (3τ to 95% step response) is small
   relative to θ and well below the chamber τ ≈ 600 s. We are not bandwidth-limited
   by the filter; we are bandwidth-limited by the plant. [VERIFIED: calibration notes
   2026-05-04, 09:33:32 pulse impulse response]
2. **Sensor noise floor ≈ 0.1 % RH** (SHT30 spec) is comparable to the per-pulse RH
   amplitude (0.13 %). Without heavy filtering, the controller chases noise.
   [VERIFIED: calibration notes line 96]
3. **Median-of-5 input pre-filter is already in place** (line 134), but at 5Hz this
   is only a 1-second median window — insufficient to suppress 0.02 %/s tick-to-tick
   variation when multiplied by Kd=4.
4. **Farmer's qualitative "magenta PWM cycling looks proportionally clean"
   observation** (calibration notes line 140) suggests the slow-PWM windowing
   already low-passes the duty signal at ~120s. A 10s filter on D is consistent
   with the system's natural time scales.

### Sweep plan (for the eventual planner / next calibration session)

| τ value | N (vs Td=11.4) | 95% step time | Expected behavior |
|---------|----------------|---------------|--------------------|
| 0.0 (disabled) | — | 0 | current — visible ±5-8% duty jitter |
| 1.14 (N=10 textbook) | 10 | 3.4 s | classic textbook tuning |
| 3.0 | ~4 | 9 s | moderate filtering |
| **10.0 (default)** | **1.14** | **30 s** | aggressive filtering — recommended starting point |
| 30.0 | 0.4 | 90 s | likely over-filtered, D becomes ineffective |

**Recommended live-tuning sequence:** start at τ=10.0, observe 30 min steady-state.
If acceptance ratio met, sweep down (3.0 → 1.14) to find the smallest τ that still
hits ≥3×. If acceptance ratio **not** met at τ=10, the diagnosis is wrong (filter
isn't the dominant noise source) — escalate.

### Live-reload contract

Live-reloadable like Kp/Ki/Kd. Use `ros2 param set /fc_controller
pid_derivative_filter_tau <value>` for live tuning; commit YAML once a value is
confirmed. Same pattern as the entries already in `pid_calibration_notes.md`.

# test_pid_kernel.py — add at bottom

def test_d_filter_noise_rejection():
    """FILT-02: synthetic noisy RH at quiet steady state — filtered D contribution
    has ≥3× lower tick-to-tick RMS than unfiltered.

    Setup: 60 ticks at dt=0.2s (12s window). Constant true input 94.0%, plus
    Gaussian noise σ=0.05% per tick (~SHT30 noise floor). τ=10.0s.
    Compare RMS of d_contribution vs RMS of -Kd · raw_d_input/dt.
    """
    import random
    random.seed(0)
    Kd, tau, dt = 4.0, 10.0, 0.2
    d_filtered, last_input = 0.0, None
    raw_contribs, filt_contribs = [], []
    for _ in range(60):
        x = 94.0 + random.gauss(0, 0.05)
        if last_input is not None:
            raw_rate = (x - last_input) / dt
            alpha = dt / (tau + dt)
            d_filtered = alpha * raw_rate + (1 - alpha) * d_filtered
            raw_contribs.append(-Kd * raw_rate)
            filt_contribs.append(-Kd * d_filtered)
        last_input = x
    raw_rms = (sum(c*c for c in raw_contribs) / len(raw_contribs)) ** 0.5
    filt_rms = (sum(c*c for c in filt_contribs) / len(filt_contribs)) ** 0.5
    ratio = raw_rms / filt_rms
    assert ratio >= 3.0, f'noise rejection {ratio:.2f}× < 3.0× target'


def test_d_filter_step_response():
    """FILT-03: step in d_input should propagate to ≥63% of step magnitude within τ seconds."""
    Kd, tau, dt = 4.0, 10.0, 0.2
    d_filtered = 0.0
    # Apply unit step: raw_rate jumps from 0 to 1.0 at t=0
    n_steps = int(tau / dt)
    for _ in range(n_steps):
        alpha = dt / (tau + dt)
        d_filtered = alpha * 1.0 + (1 - alpha) * d_filtered
    # Theoretical: 1 - (1 - α)^n ≈ 1 - e^(-1) ≈ 0.632
    assert 0.55 < d_filtered < 0.70, (
        f'step response at τ should be ~63%, got {d_filtered:.3f}'
    )

## Open Questions

1. **Should the filter differentiate `error_pct` or `current_humidity * 100`?**
   - What we know: lib uses `input` (measurement) when `differential_on_measurement=True`.
   - What's unclear: external wrapper has freedom; differentiating error means setpoint
     ramp injects a small D contribution; differentiating measurement is "purer" D-on-M.
   - Recommendation: differentiate `error_pct` initially (matches what `_pid()` was
     fed before our wrapper), revisit if setpoint-ramp D-kick observed.

2. **Should `_reset_d_filter()` be called on `target_humidity` step changes, not just
   mode transitions?**
   - What we know: D-on-measurement says no — only the measurement matters, setpoint
     changes don't kick D.
   - What's unclear: if differentiating `error_pct` (per Q1), then setpoint step DOES
     produce a derivative kick, and reset would mask it.
   - Recommendation: don't reset on setpoint changes — let the filter naturally
     attenuate the kick over τ seconds. If problematic, switch to differentiating
     measurement (Q1).

3. **Will the calibration target `Kp=0.35` stay, or revert to `Kp=0.5`?**
   - What we know: 2026-05-04 commit dropped Kp 0.5 → 0.35 in YAML. Calibration notes
     suggest this may interact with future Kd retuning.
   - What's unclear: future calibration session may revisit. Not a 999.32 question
     — filter must work across this range.
   - Recommendation: filter is gain-agnostic; works regardless of Kp/Kd choice.
