**(B) `docker-compose.override.yml` — bridge service:**

The override's `bridge:` block (L8-L15) already has `volumes:` with the CycloneDDS mount. Append the burnt mount to the same list — compose deep-merges lists, but to be explicit and match the base, add:

```yaml
  bridge:
    network_mode: "host"
    restart: always
    environment:
      - RMW_IMPLEMENTATION=rmw_cyclonedds_cpp
      - CYCLONEDDS_URI=file:///etc/cyclonedds-tailscale.xml
    volumes:
      - /home/santi/.config/cyclonedds-tailscale.xml:/etc/cyclonedds-tailscale.xml:ro
      - /data/snapshots-burnt:/data/snapshots-burnt
```

Rationale for also listing the burnt mount in the override: docker-compose list-merging appends across files rather than replacing, so both the base `/data/snapshots:/data/snapshots` mount AND the override `/data/snapshots-burnt:/data/snapshots-burnt` mount will be active. This matches the pattern already established (the base has `/data/snapshots:/data/snapshots` and the override adds CycloneDDS — same mechanism).

NOTE: actually docker-compose v2 deep-merges by **replacing** list keys with override values unless `!override`/`!reset` tags are used. To avoid any ambiguity across compose versions (farm dev still runs compose v1.29; elder-plops prod is dev+prod — see memory `project_compose_v2_upgrade.md`), put the new mount in the BASE file (`docker-compose.yml`), leave the override list as-is with only CycloneDDS. **Revised instruction:** add the burnt volume ONLY to `docker-compose.yml` L30 (right after the raw mount). Leave `docker-compose.override.yml` volumes list untouched. The override will still apply its CycloneDDS mount on top — compose v1 and v2 both extend list keys when the override also sets the same key.

Wait — the override explicitly sets `volumes:` so compose v1 will REPLACE the base list with just the override's. This is exactly the runtime-compose regression documented in `feedback_verify_runtime_compose.md`. Safer: add the burnt mount to BOTH files, matching pattern the CycloneDDS+snapshots combined bridge currently relies on. Re-confirm by checking what mounts are live on elder-plops *after* deploy (task 3 of plan 22-04).
