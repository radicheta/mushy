<objective>
Forward Plan 01's new slot-2 ROS topics (`fc1/temperature_2`, `fc1/humidity_2`) through
the Mission Control bridge to (a) WebSocket clients and (b) TimescaleDB, using the same
default-VOLATILE QoS profile that the existing slot-1 subscriptions use. This is a
pure-extension plan — copy the slot-1 block verbatim, swap topic names and telemetry
IDs.

Slot 2 must NOT use TRANSIENT_LOCAL QoS (RESEARCH Pitfall 2): slot-2 publishes are
intentionally gappy (D-03), and TRANSIENT_LOCAL would replay a stale "last value" to
late-joining clients during sensor outages, defeating the whole point of the gap.

Purpose: Without bridge forwarding, slot-2 topics exist only on the Pi's DDS and never
reach the alerter or TimescaleDB. Plan 03's SCD41 belt-and-braces watchdog (which
refreshes `scd41LastSeenMs` on slot-2 WS arrival) literally cannot fire without this
plan landing.

Output: bridge container, when rebuilt, surfaces the two new topics on the WS broadcast
path and writes them to the `telemetry` table as new topic strings (no schema change —
the `topic` column is free-form text per L585).
</objective>

```javascript
async function insertTelemetry(topic, value) {
    if (!dbReady) return;
    try {
        await pool.query(
            'INSERT INTO telemetry (time, topic, value) VALUES ($1, $2, $3)',
            [new Date(), topic, value]
        );
    } catch (err) {
        console.error('[db] insert failed:', err.message);
    }
}
```
