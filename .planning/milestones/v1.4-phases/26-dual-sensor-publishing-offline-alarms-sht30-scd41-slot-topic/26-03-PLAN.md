<objective>
Add per-physical-sensor offline alerts (`sht30`, `scd41`) to the Mission Control alerter
container. Reuse the existing PENDING→FIRING→RECOVERY state machine (`driveAlertType`),
the existing snooze + cooldown machinery, the existing Signal send path, and the existing
30s tick scheduler. The work is almost entirely additive: extend lists/maps, add one new
predicate (`isSensorSilent`), wire two new routes (sensor_health values inspection +
slot-2 WS arrival), and document the new env var.

Hybrid Option C per RESEARCH: SHT30 freshness comes EXCLUSIVELY from
`sensor_health.values.sht30_fresh` (slot 1 is ambiguous post-D-01 fallback, so direct
WS arrivals don't prove SHT30 specifically). SCD41 freshness comes from EITHER
`sensor_health.values.scd41_fresh` OR slot-2 WS arrival timestamps — the alerter ORs the
two signals so SCD41 silence is detected even if `fc_controller` itself crashes.

Defines D-04 (5-min threshold), D-05 (per-sensor granularity), D-06 (recovery message)
end-to-end. Jest tests prove each in isolation.

Purpose: Closes the 2026-04-11 incident class — a silent SHT30 outage went unnoticed for
40 min during farmer calibration. Once this lands, that exact failure mode produces a
Signal message naming the offline sensor.

Output: alerter container, when rebuilt with `docker compose up -d --build alerter`,
fires `[PROBLEM · CRITICAL] FC-1 · SHT30 offline` (or SCD41 equivalent) on extended
silence and `[RECOVERY] FC-1 · SHT30 offline back` on resumption.
</objective>
