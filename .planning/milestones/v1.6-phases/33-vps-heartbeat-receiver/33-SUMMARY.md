## What shipped

End-to-end Tier 1 outage alert pipeline:

```
fc1 / elder-plops          VPS (Hetzner Nuremberg)        elder-plops bridge        operator phone
─────────────────────      ───────────────────────────    ──────────────────────    ──────────────
mushy-heartbeat.timer ──►  mushy-heartbeat-receiver  ──►  POST /heartbeat-alert ──► Signal
  every 60s POST           detects 3min staleness         signal-cli /v2/send
  HMAC-signed              fires Tier 1 alert
  over wg-hub              dedupes 1m→5m→15m→60m
```

Live components:
- **VPS receiver** — `/opt/mushy-heartbeat-receiver/index.js`, systemd unit `mushy-heartbeat-receiver.service`, listens on `127.0.0.1:9000` + `10.66.0.1:9000` (wg-hub only — UFW blocks 9000 from public).
- **VPS state** — `/var/lib/mushy-heartbeat/last_seen.json` (atomic write), `/var/lib/mushy-heartbeat/alerts.log` (newline JSON).
- **HMAC secret** — generated by `install.sh`, 64 chars from `/dev/urandom`, stored at `/etc/mushy-heartbeat/secret` on each host (mode 640, owner root:mushy on VPS, root:root on senders), signed with SHA-256.
- **Bridge endpoint** — `POST /heartbeat-alert` in `src/mission-control/bridge/src/index.js`, mirrors alerter's `/v2/send` shape, reads `SIGNAL_SENDER`/`SIGNAL_RECIPIENT` from compose env.
- **signal-cli host loopback** — `127.0.0.1:8085:8080` added in `docker-compose.override.yml` so the host-network bridge process can reach the signal-cli container API. Alerter still talks to it on `signal-net` at `signal-cli:8080` as before.
- **Senders** — `/usr/local/bin/heartbeat-sender.sh` + `mushy-heartbeat.timer` (every 60s, `OnBootSec=30s`) on fc1 and elder-plops.

## Bugs found and fixed during deploy (caught by the deploy itself, not in scaffolding)

1. **Bridge could not reach signal-cli.** D-09 in CONTEXT said "bridge dispatches via existing signal-cli docker network." Bridge runs `network_mode: host`; `signal-cli` had no `ports:` mapping and was only on the internal `signal-net` compose network. Bridge process literally could not see it. Fix: add `ports: "127.0.0.1:8085:8080"` to signal-cli (loopback only, NOT exposed to LAN/wg-hub); bridge calls `http://localhost:8085/v2/send`. Commit `e97b499`.
2. **install.sh perms locked the service out of its own secret.** `chmod 700 /etc/mushy-heartbeat` (root-only) + `chown mushy:mushy` on data dir but secret stayed root-owned + 600. Service runs `User=mushy` and crash-looped EACCES. Fix: dir → root:mushy 750, secret → root:mushy 640. Commit `6c27610`.
3. **Tier 1 dispatch timeout was 5s — too tight.** First real fc1 silence triggered the alert correctly (3.1min) but bridge POST timed out at 5s and fell to Tier 2 placeholder. Manual curl from VPS with `-m 10` succeeded → path is healthy, signal-cli `/v2/send` is just sometimes 5–10s on a cold call. Bumped to 15s. Commit `6c27610`.

All three were latent in the scaffold; all surfaced within 10 minutes of first deploy attempt. Nothing was wrong with the scaffolded *design* (decisions D-01..D-12 all hold), but the implementation had three plumbing bugs that only the actual deploy would catch.

## Operational reference

- **Receiver health:** `ssh mushy@178.105.84.13 'curl -sS http://127.0.0.1:9000/health | jq'`
- **Last alerts:** `ssh mushy@178.105.84.13 'sudo tail /var/lib/mushy-heartbeat/alerts.log'`
- **Receiver logs:** `ssh mushy@178.105.84.13 'sudo journalctl -u mushy-heartbeat-receiver -f'`
- **Reset state:** `ssh mushy@178.105.84.13 'sudo systemctl stop mushy-heartbeat-receiver; sudo rm /var/lib/mushy-heartbeat/last_seen.json; sudo systemctl start mushy-heartbeat-receiver'`
- **Force a smoke:** `ssh fc1 'sudo systemctl stop mushy-heartbeat.timer'` then wait 3+ minutes, then re-enable with `sudo systemctl start mushy-heartbeat.timer`.
