# Phase 27.2 Plan 27.2-01: Partial close — systemd hardening shipped, full SYS-04 deferred

**fc-core.service hardened with explicit wg0 dependency and validated against the cold-reboot scenario (41s end-to-end recovery, zero manual). The wg0-down-at-boot scenario — the exact failure class from the 2026-05-02 incident — remains untested because validating it carries unrecoverable-from-elder-plops risk; folded into 999.28 to be paired with the next lab visit.**

## What shipped

- `scripts/pi-deploy/fc-core.service` now declares `After=wg-quick@wg0.service` + `Wants=wg-quick@wg0.service` explicitly (commit `3ec8d19`). The pre-existing 60×1s IPv4 polling loop is retained as belt-and-braces.
- ROADMAP.md Phase 27.2 entry: SYS-01 flipped `[x]` with corrected text ("waits for IPv4 on wg0 via polling loop", not the stale "waits on `ip link show wg0`"); SYS-03 flipped `[x]` (no longer "(partial)").
- SYS-04 scenario 1 (cold reboot): PASS evidence committed (`b7828d1`). 41s from `reboot` to `fc-core.service active (running)`, all 5 ROS nodes up, no `start-limit-hit`, zero manual intervention.

## What's deferred

- **SYS-04 scenario 2 (wg0-down-at-boot):** Validates the exact failure class from 2026-05-02 — wg0 link present, IPv4 not yet acquired, fc-core's ExecStartPre must wait. Folded into 999.28; trigger condition: next lab visit with physical access to fc1's keyboard (so a wg0-broken boot is recoverable).

## Why partial-close instead of leaving it open

`27.2-01-PLAN.md` is a single plan with three tasks. Tasks 1+2 fully done; Task 3 deferred indefinitely (gated on a precondition the operator does not hold and won't hold soon). Leaving the plan open would (a) keep STATE.md flagging Phase 27.2 as `executing` indefinitely, (b) block milestone v1.5.0.1 from advancing, and (c) hide the deferral inside an unfinished plan rather than as an explicit backlog item where it can be tracked alongside other on-lab work.

## What this teaches

This phase is itself a Phase 999.37 instance: a phase scoped a key validation (SYS-04 reboot test), the validation was deferred at original scope ("cheap to do later when fc1 is on a fresh microSD"), then when retried it surfaced an unrelated failure mode (wifi config drift) that took 11h to recover from, and the *primary* code path (wg0-not-ready-at-boot) still hasn't been exercised. The post-mortem (`.planning/notes/2026-05-07-postmortem-cold-reboot-and-buffer-replay-bug.md`) documents both the operational lessons (pre-flight wifi check) and the structural one (deferred validations are untested code).
