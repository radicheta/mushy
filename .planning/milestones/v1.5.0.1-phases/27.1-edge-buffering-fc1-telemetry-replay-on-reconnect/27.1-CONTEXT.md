# Phase 27.1: Edge Buffering — Context

**Gathered:** 2026-05-02
**Status:** Ready for planning

<domain>
## Phase Boundary

fc1 captures all `fc.*` telemetry to a local store during connectivity gaps. On bridge reconnect, the bridge pulls buffered points from fc1 and inserts them into Timescale with original timestamps, so Mission Control history shows continuous data instead of holes.

**Triggering evidence:** 2026-05-02 ~13-min Tailscale dropout (São Paulo DERP relay) caused full telemetry blackout from 00:19→00:32 UTC. PID held the chamber in lock the whole time (RH 94.0±0.04% before, 93.96% after, target 94%) — control was unaffected; only visibility was lost. With Phase 27 PID publishing high-resolution `fc.pid_output`/`fc.humidifier_duty`/`fc.humidity_target` at ~5Hz, every dropout is a permanent hole in the data we'd want for tuning and post-mortem.

**Out of scope:** changing fc1↔bridge transport (still DDS-over-Tailscale during normal operation); buffering bridge↔Timescale (Timescale is system of record, bridge writes are local); camera frame replay (handle as a separate scope decision in research).

</domain>

<decisions>
## Implementation Decisions

### Replay Protocol
- **D-01:** Bridge **polls** fc1 for buffered points. fc1 exposes a stateless HTTP endpoint along the lines of `GET /telemetry/since?ts=<ns>` returning JSONL of buffered (topic, time_ns, value, optional fields) points oldest-first.
- **D-02:** Bridge detects DDS gap (no points received on heartbeat topics for N seconds), waits for fc1 to be reachable again, then issues a `since=<last_ingested_ts>` poll. Inserts results into Timescale.
- **D-03:** Polling is idempotent and resumable — if the bridge crashes mid-replay, the next poll re-asks from `last_ingested_ts` and gets the remainder. fc1 holds nothing about bridge state.
- **D-04:** Rejected: fc1-push-on-reconnect (more state machine, harder idempotency across restart races). Rejected: CycloneDDS DURABILITY=PERSISTENT (opaque, doesn't survive fc-core restarts — see 999.25 init-race kills fc-core periodically).

### Storage Substrate
- **D-05:** SQLite with WAL mode on fc1 — one hypertable-style schema `telemetry_buffer(topic TEXT, time_ns INTEGER, value REAL, extra JSONB-as-text)` with `PRIMARY KEY (topic, time_ns)`.
- **D-06:** stdlib `sqlite3` only — no new pip dependency. WAL gives concurrent writer (the buffering node) and reader (the HTTP endpoint) without locking trouble.
- **D-07:** Indexed `since-X` query is the hot path: `SELECT topic, time_ns, value, extra FROM telemetry_buffer WHERE time_ns > ? ORDER BY time_ns LIMIT N`.
- **D-08:** Rejected: append-only JSONL (no index, long-outage replay scans more bytes; rotation logic is on us).

### Topic Scope + Retention
- **D-09:** **Capture-all** of `fc1/*` topics that the bridge currently subscribes to (mirrors `ALLOWED_TOPICS` in `src/mission-control/bridge/src/index.js`). Future derived topics from 999.27 (`/fc1/derived/*`) get buffered automatically by virtue of being in the same wildcard.
- **D-10:** **24h ring eviction** — periodic sweep (e.g. every 60s) deletes rows older than 24h. 24h is comfortably longer than any plausible Tailscale outage on a 4G+weak-wifi link, and steady-state size is predictable.
- **D-11:** Camera topic (`/fc1/camera/compressed`) is **excluded from the buffer** — image frames are too large for a ring buffer's purpose (post-mortem analysis of control loop), and Phase 22 / 999.10 already handle camera persistence and traffic-shaping. Plan should hard-exclude camera-class topics by name pattern.

### Claude's Discretion
- HTTP endpoint binding (Tailscale interface only vs all interfaces + auth) — researcher to recommend; default to **Tailscale-tailnet-only bind, no auth** (tailnet is already the trust boundary, matches existing pattern of bridge talking to fc1).
- Backfill conflict policy in Timescale: **`ON CONFLICT (topic, time) DO NOTHING`** (idempotent, simplest, matches our "memory says Timescale handles out-of-order cleanly" prior knowledge).
- Whether the buffering lives as a new ROS node in `fc_core` package or a small standalone Python service — node is more idiomatic (subscribe via DDS like every other consumer); leave to planner.
- Alerter behavior on backfilled points: probably should **not** re-evaluate alert rules on points more than M minutes old (avoid paging on resolved-old gaps) — flag for planner; touches `src/agents/alerter/src/state.js`.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- **Existing publish-side code** (`fc_sensors.py`, `fc_controller.py`, `fc_pwm_driver.py`) — buffering node only needs to *subscribe*; no changes to publishers required.
- **Existing topic catalog in bridge** (`ALLOWED_TOPICS` in `src/mission-control/bridge/src/index.js`) — single source of truth for what to buffer; mirror via shared YAML or duplicate-with-comment.
- **Existing Timescale ingest path in bridge** (`mushy-bridge-1` container) — backfill uses the same INSERT path with one `ON CONFLICT` change.
- **stdlib `sqlite3`** — already available on the Pi; no new dependency.

### Established Patterns
- **fc1-side ROS nodes register via `setup.py` entry_points + launch in `fc.launch.py`** (Plan 27-02 pattern is the freshest example for adding a new node).
- **fc1↔bridge talks DDS, not HTTP** today. The buffer adds the *first* HTTP surface on fc1 — researcher should pick the lightest server (stdlib `http.server`, `aiohttp`, or `flask` if a sync ROS thread already runs one).
- **Tailscale tailnet is the trust boundary** for cross-host fc1↔elder-plops traffic — no auth on internal endpoints (bridge already operates this way).

### Integration Points
- New ROS subscriber per buffered topic, using same QoS the bridge uses (mostly RELIABLE / TRANSIENT_LOCAL where applicable per Plan 27-04).
- Bridge gains a small "gap detector + replay puller" module (likely a new file in `src/mission-control/bridge/src/`) that calls fc1 over Tailscale.
- Timescale schema: one schema change — add `ON CONFLICT (topic, time) DO NOTHING` constraint OR rely on existing primary key if already there (planner to verify current `telemetry` table DDL).

</code_context>

<specifics>
## Specific Ideas

- Farmer's words 2026-05-02: "these connectivity gaps make the edge buffering more important — we want fc1 to dump data on reconnect, fill gaps." → emphasizes *gap-fill* (visible Mission Control charts) is the user-facing acceptance test, not just "data not lost in some database."
- Acceptance test shape (for VERIFICATION.md later): induce a 5-min Tailscale dropout (e.g. `sudo tailscale down` on fc1), wait, `sudo tailscale up`. Within ~60s of reconnect, the gap in the OpenMCT humidity chart should be filled in with the original-timestamped points — visible to the naked eye.

</specifics>

<deferred>
## Deferred Ideas

- **Camera frame buffering** — out of scope per D-11; if farmer ever wants gap-fill on camera too, that's its own phase (composes with 999.10 on-demand camera and 999.21 timelapse resolution).
- **Bridge-side buffer** (bridge → Timescale) — Timescale is local to elder-plops, so this gap is essentially never the failure mode; if elder-plops ever goes down, the loss is bounded by elder-plops uptime not network.
- **Multi-chamber generalization** — when 999.6 (multi-chamber on Pi Zeros) lands, every chamber Pi will need its own buffer. Sketch should make the buffering node parameterizable on `chamber_id` from day one to avoid a refactor.
- **Backfill-aware alerting** — alerter needs to know "this point is backfilled, don't fire fresh alerts on it." Belongs partly here (point metadata) and partly in 999.22 / 999.18 (alerter changes).

</deferred>

### D-12: Soak via natural-event observation, no synthetic induction
Today's 2026-05-02 incident already proved the failure mode (~2h cumulative
DERP-relay outages with control unaffected and visibility lost). Rather than
induce a synthetic 5-min `tailscale down`, deploy the buffer code now and let
the next natural DERP/Tailscale dropout populate VERIFICATION.md. The current
DERP-relay frequency suggests within 24-48h. **Closes BUF-04 when a real
event provides gap-fill evidence**; VERIFICATION.md lands then. Plan 04
Task 2's "induce dropout" steps become "observe next natural dropout" —
operator captures pre/post wlan0 state, dropout window, backfill metrics,
and chart screenshot when the event arrives.

**Trade-off accepted:** open-ended close-out (could be 24h, could be a week)
in exchange for stronger evidence (real event) and zero risk of operator
error during synthetic induction.
