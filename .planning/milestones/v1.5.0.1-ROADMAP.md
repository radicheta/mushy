# Milestone v1.5.0.1: Resilience Hotfix from 2026-05-02 Incident

**Status:** ✅ SHIPPED 2026-05-07 (PARTIAL — see deferrals)
**Phases:** 27.1, 27.2 (27.3 + 27.4 MOOTED by architectural detour)
**Total Plans:** 5 (4 in 27.1 + 1 in 27.2)
**Date range:** 2026-05-01 → 2026-05-07
**Code delta:** ~17 files, +1228/−46 LOC (src/ + scripts/ scope)
**Pattern:** Hotfix milestone (cf. v1.2.1) — single-incident-driven, narrow scope

## Overview

A microSD failure on fc1 on 2026-05-02 surfaced (and partly hid) a cluster of resilience gaps the prior architecture had been masking: ROS DDS routed over Tailscale's DERP relays (flaky under CGNAT), no edge-side telemetry buffer, and an fc-core systemd unit that didn't survive blackout/boot races. The original 4-phase plan (27.1 buffer, 27.2 systemd, 27.3 sampling, 27.4 netplan) was overtaken mid-flight by an **architectural detour** — fc1 was rebuilt on home-LAN wifi with a kernel-WireGuard tunnel (`wg0`) to pfSense, and DDS was moved off `tailscale0` onto `wg0`. The transport switch absorbed the SAMP justification entirely (CPU saturation gone) and parked NET (netplan drift was a farm-4G snapshot that no longer applies until fc1 returns to the farm).

What actually shipped: edge buffering with replay-on-reconnect (27.1, BUF-01..03 attested live; BUF-04 deferred to natural-event observation as 999.36) and fc-core systemd hardening (27.2, SYS-01..03 satisfied; SYS-04 scenario 1 cold-reboot PASS, scenario 2 wg0-down-at-boot deferred to 999.28).

### Phase 27.2: fc-core systemd unit hardening (PARTIAL)

**Goal:** fc-core survives blackout/boot races without manual intervention (promotes backlog 999.28).
**Depends on:** Phase 27.1 (wg0 transport must already be the DDS path).
**Plans:** 1 plan

Plans:

- [x] 27.2-01: `Restart=always` + `RestartSec=10` + `StartLimitIntervalSec=300` + `StartLimitBurst=5`; explicit `After=wg-quick@wg0.service` + `Wants=wg-quick@wg0.service`; `ExecStartPre` 60×1s IPv4-on-wg0 wait loop

**Details:**
SYS-01..03 fully satisfied. SYS-04 (validation reboot) split into two scenarios at execution time: scenario 1 (cold reboot from clean state) PASSED 2026-05-07 — fc1 boot → fc-core active in 41s with zero manual intervention. Scenario 2 (wg0-down-at-boot, simulating wg-quick failure) was deferred to backlog 999.28 because validating it requires lab LAN access — the hypothesis is that the failure mode is unrecoverable over wg0 itself (chicken-and-egg).

The same investigation also surfaced a real PID bug: `fc_controller.py:973` hardcodes `last_output=0.15` on bumpless re-engage, pinning duty cycle indefinitely if RH is in-band at restart. Tracked separately. Fixed downstream in Phase 29 plan 29-07 (`pass last_published_duty to PID bumpless re-engage` — commit `e95a599`).

## Milestone Summary

**Architectural Detour:**

- **Transport switch (2026-05-03):** DDS moved off `tailscale0` onto `wg0` (kernel-WireGuard via pfSense; 172.16.10.0/24). Followed fc1 microSD failure + rebuild on home-LAN. Absorbed SAMP entirely; parked NET. fc1 SSH access also moved to `172.16.10.5` (wg0).

**Key Decisions:**

- Decision: Promote 999.1 (edge buffering) to a milestoned phase rather than waiting for v1.5 (Rationale: 2026-05-02 incident exposed the gap as load-bearing for the v1.5 PID work)
- Decision: Switch DDS transport from `tailscale0` to `wg0` mid-milestone (Rationale: DERP-relay flakiness was making the buffer-replay deploy itself unreliable; kernel-WG sidesteps it)
- Decision: Replace BUF-04 induced-dropout recipe with natural-event observation (D-12 deferral; tracked as 999.36) (Rationale: Tailscale dropout no longer reproduces the failure mode; system became too stable to attest organically — see `project_buf04_natural_event_evidence_sweep.md`)
- Decision: Split SYS-04 into 2 scenarios; ship scenario 1, defer scenario 2 to 999.28 (Rationale: lab LAN access not available; validation declined 2026-05-07)
- Decision: Bridge buffer-replay cursor advances on live WS inserts — left as-is in this milestone (Rationale: unrelated bug surfaced 2026-05-07, tracked separately in `project_bridge_buffer_replay_cursor_bug.md`; recovery via direct fc_buffer pull worked manually for the 11h gap)

**Issues Resolved:**

- Edge telemetry buffering (BUF-01..03) — fc1 survives bridge outages and backfills on reconnect
- fc-core boot survival (SYS-01..03) — restart loop, wg-quick dependency, IPv4 wait loop
- Cold-reboot survival (SYS-04 scenario 1) — 41s farmer-attested boot → active
- DDS transport reliability — moved off DERP relays onto kernel-WG
- tailscaled CPU saturation on fc1 — eliminated by transport switch (5+ → 0.41 load avg)

**Issues Deferred:**

- **BUF-04 natural-event attestation** → 999.36 (system too stable to attest organically; needs operator-induced 10–30min outage from elder-plops side)
- **SYS-04 scenario 2 (wg0-down-at-boot)** → 999.28 (gated on lab LAN access)
- **Bridge buffer-replay cursor advance bug** — defeats backfill on reconnect (recovery used manual psql staging 2026-05-07; structural fix is a 1-line removal at bridge `index.js:613`); tracked in memory
- **PID bumpless re-engage hardcoded `last_output=0.15`** at `fc_controller.py:973` — fixed in Phase 29 plan 29-07 (commit `e95a599`); tracked outside this milestone
- **microSD wear from fc_buffer SQLite WAL** — gated on USB-SSD hardware procurement
- **`cyclonedds-tailscale.xml` filename rename** — cosmetic, tracked separately
- **999.29 max-continuous-on + cool-down redesign** — stays in v1.5 main; 0.40 → 0.90 PWM cap hotfix on `fc1/prod` (commit `ad949c6`) covers operational risk
