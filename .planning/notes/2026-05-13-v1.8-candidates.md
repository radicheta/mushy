## Part 1 -- Synthesis

### What's load-bearing and working (the asset base)

v1.7 turned the alerter from a one-way notifier into a full bidirectional pipeline: Signal capture (Phase 25/36/37) -> multimodal extraction with paid Anthropic calls (Phase 38) -> farmer single-tap confirmation loop (Phase 39) -> farmOS write path with layered idempotency (Phase 40) -> ingestion harness for regression testing (Phase 41). The state-machine lives in Timescale, watchdogs are pollers not timers (so restarts are non-events), and every paid call leaves an append-only paper trail. Compose-env passthrough is now muscle memory; em-dash discipline survived 8 plans in a row. The "smoke before paid batch" rule has saved real money twice already and surfaced Phase 40 integration gaps in 7 minutes that 92 unit tests missed.

### What's still fragile or operator-blocked (the debt)

Three operator-bound items currently gate v1.7's full close: Plan 36-04 live attestation (needs 3 farmers reachable, 30-60 min), Phase 40 dev-farmOS taxonomy seeding (and that seeding now needs schema renegotiation per the farmOS-side deliberation), and Phase 42's 4-8 week biological pilot. Beyond those: prod-farmOS is virgin territory -- v1.7 only proved the dev path, and the prod cutover needs `farmos_asset_link` install, a bot user, env-flip protocol, and prod-side alerting on write failures. signal-cli is still on deviceId=2 (linked-secondary) which has bitten three phases now; primary re-registration is the right structural fix and has been deferred long enough that it qualifies as a debt entry, not just a pre-gate. The alerter is still WS-only -- any backfilled telemetry is invisible to it, so silent downtime is detectable only by external means (uptime-kuma + ntfy, both shipped in v1.6, but neither feeds the alerter's own awareness).

### What v1.7 made possible that wasn't possible before (newly-unlocked)

Three big unlocks, in priority order. First: **the farmer's Signal stream is now a structured-data pipe**. Photo of paper log + voice note + text reply all converge to typed farmOS events without anyone doing manual entry. SEED-006 (long-arc "Signal IS the farmOS UI") is no longer aspirational, it's wired -- just one-half wired (inoc side only, harvest side pending). Second: **paid LLM is now operational infrastructure, not a science project**. Cost capping, prompt caching, smoke-before-batch, JSONL append-only -- the cost-domain discipline is mature enough that v1.8 can add Whisper-paid, Claude-vision, or any other paid path on top without re-inventing guardrails. Third: **layered idempotency is now a reusable architectural pattern**, not a one-off. State-machine layer (Phase 39) + local-cache key (Phase 40) means any future chained write path (harvest, prod-farmOS, multi-chamber telemetry batches) can compose closure at each seam.

### External pressure (what's pushing v1.8 from outside)

Three vectors. (1) ~~**farmOS-side schema shift in flight**~~ **[STRUCK 2026-05-17 -- DONE 2026-05-14]**: Zoy-side deliberation 2026-05-13 dropped `harvest_batch` as an asset and renamed `bag` -> `fruit`, plus introduced a new `fungi_xing` discriminator field. ~~This will hit mushy as a small-but-non-trivial Phase 40/41 rework~~ — relock shipped across mushy + farmOS dev + farmOS prod 2026-05-14; mushy-side checklist is 0 edits owed. (2) **Pilot calendar is sitting at zero hours**: Phase 42 can fire as soon as taxonomy seeding lands. Every week it doesn't fire is a week of v1.8 calendar pressure relieved if we ship parallel work. (3) **Vikki / Zoy availability** is the soft constraint behind any farmOS-side cooperation; the schema deliberation note was authored radicheta-side and explicitly flags "convergence question deferred" -- mushy doesn't fully control the timing.

### Candidate A -- Harvest Loop Closure

**One-line pitch:** Wire the harvest side of the multimodal pipeline so the inoc -> harvest -> yield analytics loop closes; absorb the farmOS schema migration in the same milestone.

**Why now:** v1.7 proved the inoc side end-to-end but harvest is still un-modeled in the alerter. The farmOS-side schema change (drop `harvest_batch` asset, rename `bag` -> `fruit`, introduce `fungi_xing`) is in flight right now -- absorbing it as part of a harvest-focused milestone is cheaper than doing it as a Phase 40 rework + a separate harvest milestone later. The two changes are the same change, viewed from two sides.

**Headline outcome (operator-said):** "I can take a photo of fruiting bags at harvest, voice-note the weights, and the SHI pilot's yield numbers land in farmOS without me touching a keyboard."

**Rough phase shape (originally 5 phases, now 4 after 2026-05-17 strike):**
1. ~~**Schema re-lock**~~ **[STRUCK 2026-05-17 -- shipped 2026-05-14]** ~~-- accept Zoy-side hybrid (`fungi_xing` + `fungi_type` for species + drop `harvest_batch`); update mushy seeder, alerter extractor, Phase 40 write-path. Code-only.~~
2. **Harvest extraction prompts** -- new prompt-pack for harvest events (weight per fruit, count, quality, condition). Reuse Phase 38 scorer. *(now Phase 1)*
3. **Harvest write path** -- new `commit-harvest.js` updated for the new harvest-log-aggregates-fruit-assets shape (no harvest_batch asset). Layered idempotency reused. *(now Phase 2)*
4. **Yield analytics view** -- read-side dashboard / report on `/farmer/summary` that surfaces yield per block, BE (biological efficiency) computed from substrate weight + fruit weight. *(now Phase 3)*
5. **Live attestation + dogfood** -- Don Santiago harvests one block via Signal end-to-end; smoke -> full. *(now Phase 4)*

**Risk / unknown unknown:** The harvest-side photo geometry is unproven. A photo of one fruit on a scale is easy; a photo of "11 fruits coming off block B-3 with varying weights" needs either a per-fruit photo loop (UX bookkeeping tax risk -- watch NORTH-STAR) or Claude-vision counting (accuracy unknown until tested). The biggest unknown is whether voice-note + one photo is enough, or if we need a different capture UX for harvest than for inoc.

**Effort tier: M (3-5 weeks).** Driven by the schema migration (touches alerter + farmos client + seeder + dev-farmOS provisioning) plus the new harvest-extraction surface area. Code paths are mostly parallel to existing inoc paths, so leverage is high. *(2026-05-17: schema-migration component is done; remaining harvest-extraction + write-path + analytics + dogfood likely still M in calendar terms but no longer absorbs schema-migration risk.)*

**Dependency / blocker:** (1) Zoy-side reply note closing the deliberation. (2) Phase 42 pilot getting through at least one fruiting flush so there's real harvest data to validate against (so this milestone effectively pairs with Phase 42 calendar time). (3) Live-API smoke must be in place (see Candidate C) -- this milestone touches farmOS write paths and the schema rework is exactly the class of change live-smoke catches.

**Composability:** Pairs naturally with **C (live-API smoke)** -- C should ship first or first-half-of-A. Conflicts with anything that touches `commit-harvest.js` or the farmos client. Could ship alongside **E (operator dashboard)** if the yield view in Phase 4 is folded into the dashboard.

### Candidate B -- Prod-FarmOS Cutover

**One-line pitch:** Operationalize the prod-farmOS write path; v1.7 only proved dev.

**Why now:** v1.7 deferred all prod attestations behind "dev-farmOS first." That gate has held long enough that the prod side now feels like a milestone, not a Phase 40 sub-task. Backlog already lists `farmos_asset_link` prod install as a known dependency. Every week we keep writing only to dev is a week the alerter's farmOS half is theatrical.

**Headline outcome:** "Confirmations from the farmers' phones write into the real farmOS instance the farm team actually uses, not a dev mirror."

**Rough phase shape (4 phases):**
1. ~~**Prod-side prerequisites**~~ **[PARTIALLY DONE 2026-05-14 -- prod schema seeded + lion's mane backfilled + happy-path commit attested]** -- coordinate with farm team: `farmos_asset_link` module install, bot user with required permissions, taxonomy seeded in prod (separately from dev), prod credentials provisioned in mushy `.env`. *(2026-05-17: prod schema is live per `2026-05-14-prod-cutover-complete.md` (commit `edb416c`) + Phase 40 happy-path UAT 2026-05-15 (`a1705ac`). Remaining prod-cutover scope reduces to per-farmer targeting + write-failure alerting + replay protocol.)*
2. **Env-flip protocol** -- `FARMOS_ENV=dev|prod` switch in alerter, write-path target selectable per-message at first then per-farmer, kill-switch to revert.
3. **Prod write-path alerting** -- new alerter class: "prod farmOS write failed" -> Signal to operator (NOT to farmers; this is infrastructure failure, not data failure).
4. **Backfill protocol** -- dev-stage drafts (confirmed but written to dev only) optionally replay into prod via operator-run script.

**Risk / unknown unknown:** Prod-farmOS is shared infrastructure with the farm team's other workflows -- our writes might collide with their hand-entered records in ways that don't show up on dev (different taxonomy versions, different field requirements, different validators). The biggest unknown is whether the prod instance's data shape matches dev close enough that `commit-*.js` works unchanged.

**Effort tier: S (1-2 weeks)** IF the prod-side prereqs are already done by the farm team. **M (3-5 weeks)** if mushy has to drive the prod-side install too (farm-team-availability gated). Realistic: M.

**Dependency / blocker:** Farm-team availability for prod-farmOS module install + permissions config. This is identical to the Phase 19 deferral pattern from v1.3.

**Composability:** Independent of A if A doesn't ship first -- but if A does ship first, B inherits the migrated schema for free. Conflicts with C only at the alerter-client level (a live-API smoke that hits prod is a different test than one that hits dev). Could ship alongside E.

### Candidate C -- Live-API CI Smoke Harness

**One-line pitch:** Catch the "mocked tests pass, prod fails" class of bug before it hits ship-gate.

**Why now:** Three v1.7 phases (38, 40, and the 41 audio path) shipped bugs that mocked unit tests didn't catch; the v1.7 audit explicitly recommended this as the top tooling debt for v1.8. The Phase 38 Plan 03 API-shape bugs would have been caught here for under $1. Phase 40's missing-fungi_type would have been caught here for $0.10 (no Anthropic call, just farmOS POST).

**Headline outcome:** "Every Phase that touches an external service has a 5-minute live-smoke that runs in CI / pre-deploy, costs under $5/run total across all services, and is the literal gate before ship."

**Rough phase shape (3 phases):**
1. **Live-smoke harness** -- one script per external (`smoke-anthropic.js`, `smoke-farmos-dev.js`, `smoke-signal-cli.js`, `smoke-whisper.js`); shared `--canary` fixture pattern; cost-cap env var.
2. **CI integration** -- run live-smoke on a `pre-ship` GitHub workflow gated by manual trigger; results in JSONL append-only; failure mode = block phase close.
3. **Per-phase pre-declaration** -- discuss-phase template gets a "live-smoke fixture set" field; PLAN.md required to point at one. Promote `feedback_real_data_before_ship_gate_pass` from memory to workflow gate.

**Risk / unknown unknown:** Cost creep -- the rule says ~$1-3/run with prompt caching, but four services running daily is $4-12/day = $120-360/month worst case. Need a real spend budget. Second risk: live-smoke flakes from external-service flakiness become noise that erodes the gate's credibility.

**Effort tier: S (1-2 weeks).** Mostly assembly; the patterns and fixtures exist already.

**Dependency / blocker:** None. Internal-only work.

**Composability:** **C is a prerequisite for A and B** -- the harvest milestone and prod cutover are exactly the surface area C protects. C can ship alongside any other candidate. No conflicts.

### Candidate D -- Multi-Chamber Foundation

**One-line pitch:** Make adding chamber #2 a 1-week task, not a 6-week task.

**Why now:** Memory says 3-5 chambers are coming on Pi Zero remote I/O. Today's fc1 codebase has chamber-1 assumptions baked in at multiple layers (topic names, alerter routing, dashboard, Timescale schema, mode storage). The marginal cost of fixing each layer at chamber-2-time is the cost of doing it now plus the cost of having to re-test chamber-1 each time. Doing it now amortizes.

**Headline outcome:** "We add an outdoor log chamber by editing one config file and plugging in one Pi Zero; nothing else changes."

**Rough phase shape (5 phases):**
1. **Topic + schema generalization** -- `fc1/*` -> `chamber/<id>/*`, Timescale columns add `chamber_id`, migration scripts for existing 6 months of data.
2. **Mode + scheduler per chamber** -- modes block becomes `chambers.<id>.modes.*`; controller reads its own subtree.
3. **Alerter multi-chamber routing** -- alerts include `chamber_id`; farmer-map can be per-chamber or global; Signal messages prefixed.
4. **Mission Control multi-chamber view** -- panel-per-chamber; one health panel each; one set of charts each.
5. **Pi Zero bring-up runbook** -- first remote-I/O chamber on real hardware; smoke -> dogfood.

**Risk / unknown unknown:** The Timescale migration of 6+ months of `fc1`-named data is the scariest part -- rename-or-copy decisions, downtime windows, backup-first protocol. Second risk: Pi Zero's RAM / CPU might not host a full fc_core node; might need a thinner remote-I/O daemon and central controller pattern (which is a bigger architectural shift).

**Effort tier: L (6+ weeks).** Driven by the schema migration + the architectural question (each-chamber-runs-fc_core vs central-controller-with-remote-I/O) + real hardware bring-up.

**Dependency / blocker:** None internally. Pi Zero hardware acquisition. Operator clarity on architecture (each-chamber-has-Pi vs central-Pi-with-remote-I/O).

**Composability:** Conflicts with anything that touches the alerter routing layer (so A and B want to ship first or after, not concurrent). Pairs naturally with E (dashboard surface) because the dashboard work compounds.

### Candidate E -- Operator Morning Dashboard

**One-line pitch:** Daily-view artifact for Don Santiago that surfaces drift, pending confirmations, anomalies -- one page, 30 second skim.

**Why now:** v1.7 introduced a confirmation-pending state and dev/prod-farmOS divergence and a paper trail across ~6 services. The operator currently has to remember to check 4 places (Mission Control panels, Signal threads, fc1 ssh status, farmos web UI). A daily dashboard is the inverse of the WS-only alerter blindspot: the alerter pushes critical alerts; the dashboard pulls everything else into one view.

**Headline outcome:** "I make coffee, glance at the dashboard, see 'all green, 2 pending confirmations from Vikki on a recent inoc batch', and I know the day's status in 30 seconds."

**Rough phase shape (4 phases):**
1. **Backend rollup** -- new `/operator/morning` JSON endpoint in bridge; pulls from Timescale + farmOS + alerter signal_draft state + uptime-kuma.
2. **Dashboard UI** -- vanilla HTML/CSS/JS (Phase 18 farmer dashboard pattern); served from bridge `/operator`.
3. **Drift surfaces** -- 24h RH band stats, ALRT cooldown counts, paid Anthropic spend last 24h, pending confirmations count, sensor disagreement (SHT30 vs SCD41 once SHT30 returns).
4. **Morning-checklist mode** -- explicit "what needs me today" section: pilot events due, farmer pings outstanding > 24h, calibration overdue, etc.

**Risk / unknown unknown:** The single biggest UX risk is that this becomes a passive "looks fine" page that nobody actually checks. Mitigation: pair with a once-per-morning Signal nudge or ntfy ping with a 1-line summary + link to full page. Second risk: scope creep -- "while we're at it" rabbit holes. Keep the v1.8 cut to 4 sections max.

**Effort tier: S (1-2 weeks).** Pattern is well-known (farmer dashboard precedent); read-only; no schema work.

**Dependency / blocker:** None. Could start today.

**Composability:** Compounds with literally every other candidate -- yield numbers from A, prod-write status from B, smoke-run pass/fail from C, multi-chamber rollup from D, cost-spend telemetry from F, group-thread state from G. The dashboard is the natural integration surface.

### Candidate F -- Cost Telemetry & Spend Guardrails

**One-line pitch:** Track every dollar of paid Anthropic / Whisper-cloud / farmOS-hosting; alert on anomalies; surface per-session attribution.

**Why now:** v1.7 introduced paid Anthropic calls as production infrastructure. Today the only spend visibility is reading JSONL files. There's no monthly view, no per-farmer attribution, no spike alert. With Candidate A (harvest) adding more LLM calls, and Candidate C (live-smoke) adding daily LLM ping, spend is going to grow.

**Headline outcome:** "I open the dashboard and see this month is at $32, projecting $48, with 78% from Phase 38 extractions and the rest from live-smoke; one farmer's session cost $0.40 because they had 6 photos."

**Rough phase shape (3 phases):**
1. **Spend ledger** -- new `paid_api_call` Timescale table; every paid call writes one row with (service, model, tokens_in, tokens_out, cost_usd, draft_id, farmer_slug, run_id). All Phase 38/39/40 paid paths instrumented.
2. **Monthly view + per-session attribution** -- aggregation views + cost-per-draft / cost-per-farmer rollups. Surface in operator dashboard (Candidate E) if shipped.
3. **Anomaly alerter** -- daily-spend > 2x trailing-7d median -> operator Signal alert. Same surface as ntfy.sh outage alert.

**Risk / unknown unknown:** Anthropic doesn't expose per-call dollar cost in the response (you compute from tokens + pricing-table). Pricing-table drift over time means historical re-runs of cost numbers will be approximate. Probably fine; just be honest about it.

**Effort tier: S (1-2 weeks).** Mostly instrumentation + view; no new external integration.

**Dependency / blocker:** None.

**Composability:** Natural pairing with E. Independent of others. No conflicts.

### Candidate G -- Multi-Farmer Routing & Group-Thread UX (999.20)

**One-line pitch:** Make confirmations work cleanly when 2-3 farmers share a thread; close the long-deferred 999.20.

**Why now:** v1.7 ships single-farmer confirmation. Phase 39 D-06a explicitly DM-pings even for group-originated drafts because group-confirm UX is undecided. Real Mossrock workflow has 3 farmers + bot in the same Signal group; the group-DM split is jarring. v1.7's audit flagged this as the highest-value behavioral gap.

**Headline outcome:** "Vikki posts a photo to the farm group, the bot replies in-group asking who's confirming, Selina taps YES in-group, the draft commits, everyone sees what happened -- no DM split."

**Rough phase shape (4 phases):**
1. **Group-confirm routing decision** -- one of: (a) bot DMs the captor, (b) bot replies in-group and accepts any farmer's confirmation, (c) bot replies in-group and only accepts the captor's confirmation. UX decision, then code.
2. **In-group preview message format** -- "@Vikki sent this -- reply YES/NO/EDIT to confirm" with appropriate mention semantics.
3. **Multi-farmer attribution** -- `signal_draft.confirmed_by_farmer_slug` separate from `captured_by_farmer_slug`; audit trail shows who did which step.
4. **Live attestation** -- group-mode dry run with f1/f2/f3 in a real Signal group.

**Risk / unknown unknown:** Signal-cli group-mention semantics are reportedly flaky (memory has multiple linked-device gotchas). The biggest unknown is whether `@mention` actually works on the bot's deviceId=2 path or needs the primary re-registration too.

**Effort tier: S (1-2 weeks).** Small scope, well-defined.

**Dependency / blocker:** Depends on signal-cli primary re-registration (still deferred). Could ship without if we accept deviceId=2 mention limitations, but might be a half-cooked deliverable.

**Composability:** Independent of A, B, C, D, F. Pairs with E (showing group state in the dashboard).
