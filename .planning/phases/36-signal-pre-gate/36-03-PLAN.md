<objective>
Build the only piece of long-lived enforcement infrastructure Phase 36 ships: `scripts/signal/post-rebuild-trust-check.sh`. This script is the answer to Success Criterion #3 — "alerter container rebuild does not break identity trust." Without this script, that property is unverified on every future rebuild.

Purpose: D-08 + D-10 (CONTEXT.md). Three-branch behavior:
1. Live fingerprint == known-good AND trust table clean → exit 0, log `{verdict: ok}`
2. Live fingerprint == known-good BUT trust table stale (rebuild-corruption case per memory `project_signal_cli_rebuild_breaks_trust`) → apply `trust_all_known_keys=true` curl, re-check, exit 0, log `{verdict: recovered}`
3. Live fingerprint != known-good (key actually changed — should not happen post-Phase-36) → exit non-zero, log `{verdict: hard_mismatch}`, do NOT auto-trust (per D-06: initial re-acceptance is farmer-manual)

Output: Script + test suite + wire-up in alerter compose. Plan 36-04 will exercise this script in the rebuild-attestation step.
</objective>

Endpoint surface for the script:
- `GET /v1/identities/+<BOT>` — returns `[{number, fingerprint, safety_number, trust_level, added}, ...]`
- `PUT /v1/identities/+<BOT>/trust/+<RECIPIENT>?trust_all_known_keys=true` — applies trust for one recipient
- Iterating: get identities, for each `number` field, PUT trust if `trust_level != "TRUSTED_VERIFIED"` (or whichever value signal-cli uses for accepted).

The "known-good fingerprint" is the bot's OWN identity fingerprint as observed POST re-registration (Plan 36-02 captures `identities-postreg-YYYYMMDD.json`). The script compares the live bot fingerprint to this pinned value. Per-farmer trust drift is what gets auto-recovered; bot-key change is the hard failure.

`docker-compose.override.yml` alerter service:
- network_mode: not host (uses `signal-net` + `default` compose networks)
- mounts: `/data/signal-capture:/data/signal-capture` (we'll add `./scripts/signal:/opt/scripts/signal:ro`)
- runs node receive-loop; no native bash entrypoint wrapper currently

Wire-up decision (per CONTEXT.md Claude's Discretion): use a **healthcheck**. Reason: alerter's restart policy is `unless-stopped`; a healthcheck that fails on hard_mismatch will mark the container unhealthy without restarting it (giving the operator a clean signal without a restart loop). The script must be idempotent and fast (<5s) to fit in a healthcheck cadence.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| alerter container → signal-cli | Trusted compose-net path; both containers are operator-controlled. Threat surface is small (no external input) |
| script → known-good baseline | The baseline is a file in repo; tampering with it is a repo-write authentication problem, not in scope for this script |
| script → trust PUT endpoint | Auto-trust is bounded to recipients already present in the identity DB (signal-cli won't accept trust for unknown numbers); blast radius = re-trusting an existing-but-stale row |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-36-01 | Tampering | scripts/signal/known-good-identity.json | accept | Tampering requires repo write access; outside script's threat model. Operator review of repo changes is the control |
| T-36-02 | Elevation | trust_all_known_keys curl auto-application | mitigate | Script never auto-trusts when bot fingerprint mismatches known-good (D-06); auto-trust only fires on per-recipient stale rows (rebuild-corruption case per memory `project_signal_cli_rebuild_breaks_trust`) |
| T-36-03 | DoS | Signal-cli unreachable → healthcheck flap | accept | Healthcheck `retries: 2` + 5min interval ensures transient flaps don't churn; verdict=signal_cli_unreachable is logged so operator can investigate |
| T-36-04 | Repudiation | Script applies trust silently | mitigate | Structured JSON log line emits `verdict=recovered` + `recipients_recovered: N` on every recovery; operator can audit by grepping container logs |
</threat_model>
