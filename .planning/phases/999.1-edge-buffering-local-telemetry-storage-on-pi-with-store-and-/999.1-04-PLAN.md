<task type="checkpoint:human-verify" gate="blocking">
  <name>Task 2: Induced Tailscale dropout soak — farmer-attestable acceptance test</name>
  <what-built>
    fc_buffer running on fc1 captures every fc1/* telemetry message to local SQLite. Bridge polls every 30s and backfills Timescale with `ON CONFLICT DO NOTHING` at the original DDS timestamps. The acceptance scenario: induce a ~5min Tailscale dropout on fc1, wait, restore Tailscale, watch the gap fill in OpenMCT within ~60s of reconnect with original-timestamped points (not a step at reconnect time).
  </what-built>
  <how-to-verify>
    Operator runs the soak. Steps:

    1. **Open OpenMCT** in a browser: `http://100.96.10.66:8080/` (or whatever the operator uses today). Pin the Humidity chart to a 30-min window so the soak period is fully visible.

    2. **Note baseline state** — record current time T0, latest humidity value, latest fc_buffer row count:
       ```bash
       date -u +%FT%TZ
       ssh fc1-ts 'sqlite3 /var/lib/fc-core/buffer.sqlite "SELECT topic, COUNT(*), MAX(time_ns) FROM telemetry_buffer GROUP BY topic;"'
       docker exec mushy-timescale-1 psql -U postgres -tAc "SELECT MAX(time) FROM telemetry WHERE topic='fc.humidity';"
       ```

    3. **Induce dropout** on fc1 (DO NOT touch wlan0 per memory feedback_no_interface_down). Sequence:

       3a. **PRE-TEST GUARDRAIL — wlan0 must be UP before we touch anything** (abort if this fails):
       ```bash
       ssh fc1-ts 'ip link show wlan0 | grep -q "state UP"' || { echo "ABORT: wlan0 not UP before test — do not proceed"; exit 1; }
       ssh fc1-ts 'ip link show wlan0 | grep -E "state UP|state "'   # capture state for VERIFICATION.md
       ```

       3b. **Bring tailscale down** (this is the ONLY interface manipulation allowed):
       ```bash
       ssh fc1-ts 'sudo tailscale down'
       ```

       3c. Confirm bridge can no longer reach fc1: `curl -sf --max-time 3 "http://100.96.239.75:8765/telemetry/since?ts=0&limit=1"` should fail/time out from elder-plops. WS in OpenMCT humidity chart should stop receiving live points within ~10s.

    4. **Hold dropout for 5 minutes**. During this window:
       - Observe OpenMCT humidity chart — last live point should be from just before T_dropout, then a flat-line / no-new-data state.
       - Confirm fc1 buffer is still capturing locally (NOTE: SSH still works because fc1 also has LAN; if SSH is unreachable during this window, that itself is a wlan0/LAN concern — do NOT escalate by touching interfaces, just wait for the test to finish):
         ```bash
         ssh fc1-ts 'sqlite3 /var/lib/fc-core/buffer.sqlite "SELECT COUNT(*), MAX(time_ns) FROM telemetry_buffer WHERE topic=\"fc.humidity\";"'
         ```
         Row count should be growing; max time_ns should be advancing in real-time.

    5. **Restore Tailscale** on fc1, then **POST-TEST GUARDRAIL**:
       ```bash
       ssh fc1-ts 'sudo tailscale up'
       date -u +%FT%TZ   # T_reconnect

       # POST-TEST GUARDRAIL — wlan0 MUST still be UP (proves tailscale up did not touch wlan0):
       ssh fc1-ts 'ip link show wlan0 | grep -q "state UP"' || { echo "FAIL: wlan0 is not UP after tailscale up — investigate immediately"; exit 1; }
       ssh fc1-ts 'ip link show wlan0 | grep -E "state UP|state "'   # capture state for VERIFICATION.md
       ```

       Both pre and post wlan0 captures MUST be recorded in VERIFICATION.md as proof that the only interface touched was tailscale0. If either guardrail fails, halt the soak and surface to operator.

    6. **Within 60s of reconnect**: refresh the OpenMCT humidity chart. The 5-min gap MUST fill in with points carrying the ORIGINAL timestamps (i.e. continuous data shape from T_dropout through T_reconnect, not a vertical step or a cluster at T_reconnect).

    7. **Verify backfill metrics**:
       ```bash
       docker logs --tail 50 mushy-bridge-1 | grep buffer-replay
       docker exec mushy-timescale-1 psql -U postgres -c "SELECT COUNT(*) FROM telemetry WHERE topic='fc.humidity' AND time BETWEEN '<T_dropout>' AND '<T_reconnect>';"
       ```
       Expect: `[buffer-replay] backfilled N rows ...` log lines after reconnect; row count for the dropout window > 0 (at typical 0.5–1Hz humidity, expect 150–300 rows in 5 min).

    8. **No alerts fired** during the dropout window: check Signal — `mushy-alerter` should NOT have sent a "sensor offline" page (the existing Pi/sensor-offline alerters are 10-min thresholds per memory project_alerter_rh_two_source_bug; a 5-min dropout is below that floor). If an alert DID fire, that's the existing alerter's behavior, not a buffer regression.

    9. **Record measurements in VERIFICATION.md**: T_dropout, T_reconnect, backfilled row count, max replay latency (T_first_backfill_log - T_reconnect), screenshot of the chart with the now-filled gap, **pre-test wlan0 state output**, **post-test wlan0 state output** (both must show `state UP`).

    10. **Farmer attestation**: forward the screenshot via Signal asking "data continuity OK?". Capture response in VERIFICATION.md.
