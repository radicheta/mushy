**Researched:** 2026-05-02
**Domain:** ROS2/rclpy on Pi + SQLite buffer + Node.js bridge HTTP poller + Timescale idempotent ingest
**Confidence:** HIGH (all decisions locked; touchpoints verified in repo; one Timescale schema gotcha discovered during research)

## Summary

The bridge polls fc1 via stateless HTTP, fc1 writes a small SQLite ring buffer of all `fc1/*` topics it currently DDS-subscribes to, and on reconnect the bridge backfills Timescale with `ON CONFLICT DO NOTHING`. The work is small (~one new ROS node, one new bridge module, one schema migration) but has three load-bearing details that must not be missed:

1. **Timescale `telemetry` table currently has NO PRIMARY KEY or UNIQUE constraint** — `ON CONFLICT (topic, time)` will throw `there is no unique or exclusion constraint matching the ON CONFLICT specification`. A migration is required as a Wave-1 task. **(VERIFIED via `\d telemetry` against live `mushy-timescale-1` 2026-05-02.)**
2. **The bridge's existing `insertTelemetry()` writes `new Date()` (NOW), not the DDS message timestamp.** Backfill replay needs a parameterized `insertTelemetry(topic, value, timestampMs)`; live inserts can keep their current call-site behavior or switch to `msg.header.stamp` — the latter is a small improvement worth bundling but easy to descope.
3. **Mirroring `ALLOWED_TOPICS` from JS to Python is brittle.** Plan should use a shared YAML/JSON config (`config/buffered_topics.yaml`) that both bridge and the new fc1 node load — adding a new topic in Phase 999.27 should not require touching the buffer code.

**Primary recommendation:** New ROS node `fc_buffer` in `fc_core` package (mirrors Plan 27-02 `fc_pwm_driver` shape). Stdlib `http.server` in a daemon thread (no new deps). SQLite with WAL, single writer, the HTTP server reads via a separate connection. Bridge gets a new module `src/mission-control/bridge/src/buffer-replay.js` that runs a 30s polling loop against `http://fc1-ts:8765/telemetry/since?ts=<ns>` and inserts via the new parameterized path. Schema migration adds `UNIQUE (topic, time)` to Timescale `telemetry`.

### Pattern 1: New rclpy node with subscribers + background thread

```python
# Source: derived from src/chambers/fc-core/fc_core/fc_pwm_driver.py (Plan 27-02)
import threading, sqlite3, json, http.server, socketserver, yaml
import rclpy
from rclpy.node import Node
from rclpy.qos import QoSProfile, DurabilityPolicy, ReliabilityPolicy, HistoryPolicy

# Message-class registry — keyed by string from YAML
from sensor_msgs.msg import Temperature, RelativeHumidity
from std_msgs.msg import Float32, Bool
from diagnostic_msgs.msg import DiagnosticStatus

MSG_CLASSES = {
    'sensor_msgs/Temperature': Temperature,
    'sensor_msgs/RelativeHumidity': RelativeHumidity,
    'std_msgs/Float32': Float32,
    'std_msgs/Bool': Bool,
    'diagnostic_msgs/DiagnosticStatus': DiagnosticStatus,
}

class FcBuffer(Node):
    def __init__(self):
        super().__init__('fc_buffer')
        self.declare_parameters('', [
            ('db_path', '/var/lib/fc-core/buffer.sqlite'),
            ('http_bind', '100.96.239.75'),  # Tailscale interface only
            ('http_port', 8765),
            ('retention_seconds', 86400),
            ('prune_interval_seconds', 60.0),
            ('topics_config', '/opt/ros/.../buffered_topics.yaml'),
        ])
        self._db_lock = threading.Lock()
        self._db = sqlite3.connect(self.get_parameter('db_path').value, check_same_thread=False)
        self._db.execute('PRAGMA journal_mode=WAL')
        self._db.execute('PRAGMA synchronous=NORMAL')   # WAL-safe; faster than FULL
        self._db.execute('''CREATE TABLE IF NOT EXISTS telemetry_buffer (
            topic TEXT NOT NULL, time_ns INTEGER NOT NULL,
            value REAL, extra TEXT,
            PRIMARY KEY (topic, time_ns)
        )''')
        self._db.commit()

        # Subscribe per buffered_topics.yaml
        topics = yaml.safe_load(open(self.get_parameter('topics_config').value))
        for t in topics['buffered']:
            cls = MSG_CLASSES[t['msg_type']]
            qos = self._qos_for(t.get('qos', 'default'))
            self.create_subscription(cls, t['ros_topic'],
                lambda m, topic=t['bridge_topic']: self._on_msg(topic, m), qos)

        self.create_timer(self.get_parameter('prune_interval_seconds').value, self._prune)
        threading.Thread(target=self._serve_http, daemon=True).start()

    def _on_msg(self, topic, msg):
        # Extract scalar value + timestamp using same shape bridge uses
        ts_ns, value, extra = self._extract(topic, msg)
        with self._db_lock:
            self._db.execute(
                'INSERT OR IGNORE INTO telemetry_buffer (topic, time_ns, value, extra) VALUES (?,?,?,?)',
                (topic, ts_ns, value, extra)
            )
            self._db.commit()
```

### Pattern 2: HTTP `/telemetry/since` (oldest-first JSONL stream)

```python
# Source: stdlib http.server pattern; query shape per CONTEXT D-07
class _Handler(http.server.BaseHTTPRequestHandler):
    def do_GET(self):
        # Parse ?ts=<ns>&limit=<N>
        from urllib.parse import urlparse, parse_qs
        q = parse_qs(urlparse(self.path).query)
        try:
            since = int(q.get('ts', ['0'])[0])
            limit = min(int(q.get('limit', ['10000'])[0]), 50000)
        except ValueError:
            self.send_error(400, 'bad ts/limit'); return
        self.send_response(200)
        self.send_header('Content-Type', 'application/x-ndjson')
        self.end_headers()
        # Use a SECOND read-only connection (WAL allows concurrent reads)
        ro = sqlite3.connect(f'file:{db_path}?mode=ro', uri=True)
        try:
            for row in ro.execute(
                'SELECT topic, time_ns, value, extra FROM telemetry_buffer '
                'WHERE time_ns > ? ORDER BY time_ns LIMIT ?', (since, limit)):
                self.wfile.write((json.dumps({
                    'topic': row[0], 'time_ns': row[1],
                    'value': row[2], 'extra': row[3]
                }) + '\n').encode())
        finally:
            ro.close()
```

### Pattern 3: Bridge-side polling + idempotent backfill

```javascript
// Source: NEW src/mission-control/bridge/src/buffer-replay.js
const http = require('http');
const fs = require('fs');

const FC1_URL = process.env.FC1_BUFFER_URL || 'http://fc1-ts:8765';
const POLL_INTERVAL_MS = 30 * 1000;
const STATE_FILE = '/var/lib/bridge/buffer-replay.state.json';
const BATCH_LIMIT = 10000;

function loadLastTs() {
    try { return JSON.parse(fs.readFileSync(STATE_FILE)).last_ingested_ns; }
    catch { return 0; }
}
function saveLastTs(ns) {
    fs.writeFileSync(STATE_FILE, JSON.stringify({ last_ingested_ns: ns, updated_at: Date.now() }));
}

async function pollOnce({ pool }) {
    const sinceNs = loadLastTs();
    const url = `${FC1_URL}/telemetry/since?ts=${sinceNs}&limit=${BATCH_LIMIT}`;
    const lines = await fetchNdjson(url);  // returns string[]; throws on network error
    if (lines.length === 0) return { rows: 0 };

    let maxTs = sinceNs;
    const client = await pool.connect();
    try {
        await client.query('BEGIN');
        for (const line of lines) {
            const r = JSON.parse(line);
            const tsMs = Math.floor(r.time_ns / 1_000_000);
            await client.query(
                `INSERT INTO telemetry (time, topic, value)
                 VALUES (to_timestamp($1::double precision / 1000), $2, $3)
                 ON CONFLICT (topic, time) DO NOTHING`,
                [tsMs, r.topic, r.value]
            );
            if (r.time_ns > maxTs) maxTs = r.time_ns;
        }
        await client.query('COMMIT');
    } catch (e) {
        await client.query('ROLLBACK');
        throw e;
    } finally {
        client.release();
    }
    saveLastTs(maxTs);
    return { rows: lines.length, maxTs };
}

function start({ pool }) {
    setInterval(() => {
        pollOnce({ pool }).catch(e => console.error('[buffer-replay]', e.message));
    }, POLL_INTERVAL_MS);
}

module.exports = { start, pollOnce };
```

### Anti-Patterns to Avoid

- **Single SQLite connection across writer + HTTP reader:** even with WAL, sharing one connection across threads requires `check_same_thread=False` AND explicit locking. Use *two* connections — one writer (held by the rclpy callback, serialized by `_db_lock`), one *read-only* (`mode=ro`) per HTTP request.
- **Holding the SQLite write lock during HTTP serving:** would stall all 5Hz subscribers during a long replay. Read connection must be separate.
- **Using `fetch()` in Node.js without an explicit timeout:** during the very Tailscale outage we're solving for, an HTTP request to fc1 can hang indefinitely. Use `http.request` with an explicit `req.setTimeout(15000)` and `req.on('timeout', () => req.destroy())`.
- **Re-publishing backfilled values on the live WS:** would cause Mission Control to render duplicate points and confuse the alerter (which it doesn't subscribe to historical Timescale, but does subscribe to the live WS). Backfill writes to Timescale ONLY — WS broadcast happens at live-receive time only.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---|---|---|---|
| Out-of-order time-series ingest | Custom dedupe in bridge | Timescale `UNIQUE (topic, time)` + `ON CONFLICT DO NOTHING` | Atomic at DB level; survives bridge bug/restart races |
| Concurrent SQLite read/write | File locks, mutexes around the whole DB | SQLite WAL mode + separate `mode=ro` connection | WAL was built exactly for this; one PRAGMA, no app code |
| HTTP server with one endpoint | Hand-coded socket parser | `http.server.BaseHTTPRequestHandler` (stdlib) | One class, one `do_GET`; battle-tested |
| Streaming JSONL | Build then send a giant array | Iterate cursor + `wfile.write(line)` | Constant memory; backfilling 13 minutes × 10 topics × 5Hz = ~39k rows is small but the pattern matters for longer outages |
| Last-ingested cursor | DB table on bridge side | `/var/lib/bridge/buffer-replay.state.json` (single int) | One file write per poll; survives restart; trivially debuggable |
| Bridge↔fc1 transport | Reinvent over WS or DDS | Plain HTTP GET | Stateless, idempotent, no session, easy to curl-debug |

**Key insight:** Every component in this design has a stdlib answer. The most over-engineered version of this (gRPC, message queue, custom dedupe) would be 5x the code and harder to debug under exactly the failure mode it's solving for.

## Common Pitfalls

### Pitfall 1: `ON CONFLICT` against a table without a UNIQUE constraint

**What goes wrong:** `INSERT ... ON CONFLICT (topic, time) DO NOTHING` raises `there is no unique or exclusion constraint matching the ON CONFLICT specification`. Every backfill row fails; bridge logs but no data lands.
**Why it happens:** PostgreSQL's `ON CONFLICT` requires a real constraint, not just a non-unique index. The current `idx_telemetry_topic_time` is a regular btree.
**How to avoid:** Wave-1 task = run schema migration to add `UNIQUE (topic, time)`. Before the migration runs, scan for duplicates: `SELECT topic, time, COUNT(*) FROM telemetry GROUP BY 1,2 HAVING COUNT(*) > 1`. Either dedupe or accept losing one of each duplicate.
**Warning signs:** Bridge startup logs `[db] Schema init failed:` with the constraint-mismatch error; backfill row count stays 0 after a known-good replay test. **[VERIFIED 2026-05-02 against live mushy-timescale-1.]**

### Pitfall 2: Live `insertTelemetry()` writes `Date.now()`, not message timestamp

**What goes wrong:** Today's `insertTelemetry(topic, value)` always writes `new Date()` for the `time` column. If the same path is used for backfill, replayed points get the bridge's clock-at-replay-time instead of the original DDS timestamp — the chart hole stays.
**Why it happens:** The current bridge never had a reason to preserve message timestamps; live latency is small and `NOW()` was good enough.
**How to avoid:** Refactor `insertTelemetry(topic, value, timestampMs = Date.now())` and pass through. Backfill always supplies the original. Live path can keep the default OR (better) pass `msg.header.stamp` for `RelativeHumidity`/`Temperature`. **The latter is a small live-path improvement worth bundling — do it as one explicit task in the plan or descope to a follow-up; do NOT silently mix.**
**Warning signs:** During acceptance test, the gap fills but with a wrong (later) timestamp — the chart looks like all backfilled points landed at reconnect-time, not at original-time.

### Pitfall 3: 999.25 init race kills `fc_buffer` along with the rest of fc-core

**What goes wrong:** When `rmw_create_node` fails at boot, *all* fc_core nodes exit 1 — including the new buffer. Any in-flight messages from the ~1-minute window are lost.
**Why it happens:** Phase 999.25 documents this race; it is unfixed. `Restart=always` masks but doesn't eliminate.
**How to avoid:** Accept the loss for v1. SQLite-on-disk persists across the restart, so historical data is intact; only the messages between fc-core crash and fc-core restart are lost — which is also when the publishers (fc_sensors, fc_controller) are themselves dead, so there are no messages to capture. **Net effect: zero added data loss vs. the status quo.** Document this in VERIFICATION as a known non-issue.
**Warning signs:** Don't conflate "buffer node crashed" with "buffer failed to capture during a Tailscale outage" — they're different failure modes.

### Pitfall 4: Hardcoded topic list drift

**What goes wrong:** Phase 999.27 adds 5 derived topics. Bridge gets them; buffer doesn't. Next outage = no derived telemetry in the gap-fill.
**Why it happens:** Bridge's `ALLOWED_TOPICS` lives in JS, fc_buffer's lives in Python. Two-place edit, easy to miss one.
**How to avoid:** Single source — `config/buffered_topics.yaml`. Bridge loads it on boot (5 lines of `js-yaml` or `JSON.parse(fs.readFileSync())`); fc_buffer loads it on init. The bridge's `ALLOWED_TOPICS` (currently used as a SQL allowlist for `/history/:topic`) can derive from the same file.
**Warning signs:** New topic appears in Mission Control live but not in gap-fill backfills.

### Pitfall 5: HTTP request hangs during the very outage we're solving

**What goes wrong:** Bridge polls fc1, fc1 is unreachable, default Node.js HTTP request waits forever; the polling loop stalls.
**Why it happens:** Node's `http.request` has no default timeout.
**How to avoid:** Always set `req.setTimeout(15000)` + `req.on('timeout', () => req.destroy(new Error('timeout')))`. Catch and log; the next 30s poll will retry naturally.
**Warning signs:** Bridge logs go silent on `[buffer-replay]`; no backfill happens after a long outage even though fc1 is back up.

### Pitfall 6: GIL contention from a busy HTTP server

**What goes wrong:** Hypothetically, if Mission Control hammered `/telemetry/since` continuously, the HTTP thread could starve the rclpy spin loop and 5Hz subscribers might drop messages mid-callback.
**Why it happens:** CPython GIL — only one thread executes Python bytecode at a time.
**How to avoid (low-priority — this is unlikely to bite at our scale):** The bridge polls every 30s; the response is fast (<100ms typical). Keep `BATCH_LIMIT=10000` so a single GET completes promptly. If concerns surface, lower `prune_interval_seconds` cost by running it in the same callback timer rather than a separate thread.
**Warning signs:** `fc_sensors` warnings about late callbacks coinciding with `/telemetry/since` requests.

### Pitfall 7: SQLite WAL files (`-wal`, `-shm`) need write permission to the *directory*

**What goes wrong:** SQLite WAL mode creates two sidecar files next to the DB. If the rclpy process can write to `/var/lib/fc-core/buffer.sqlite` but not the directory, WAL silently downgrades or fails.
**Why it happens:** Common deployment oversight — a service user owns the file but not its parent.
**How to avoid:** systemd unit / deploy script ensures `chown ubuntu:ubuntu /var/lib/fc-core/`.

### Pitfall 8: Tailscale-only HTTP bind on a host that may not have `tailscale0` up at boot

**What goes wrong:** `bind('100.96.239.75', 8765)` raises `OSError: Cannot assign requested address` if `tailscale0` isn't up yet.
**Why it happens:** Same root cause as 999.25.
**How to avoid:** Either (a) the existing systemd `ExecStartPre` already waits for `tailscale0` (verified — `scripts/pi-deploy/fc-core.service:16-26`); the new node inherits that gate. (b) Bind to `0.0.0.0` and rely on the Tailscale ACL + UFW for access control. **Recommend (a)** to honor the locked CONTEXT discretion default ("Tailscale-tailnet-only bind").

```python
# Source: derived from bridge insertTelemetry call sites (index.js:609-751)
def _extract(self, bridge_topic, msg):
    """Return (time_ns, value_float, extra_json_or_none)."""
    now_ns = self.get_clock().now().nanoseconds
    if hasattr(msg, 'header') and msg.header.stamp.sec:
        ts_ns = msg.header.stamp.sec * 1_000_000_000 + msg.header.stamp.nanosec
    else:
        ts_ns = now_ns

    if isinstance(msg, RelativeHumidity):
        return ts_ns, msg.relative_humidity * 100.0, json.dumps({'frame_id': msg.header.frame_id}) if msg.header.frame_id else None
    if isinstance(msg, Temperature):
        return ts_ns, float(msg.temperature), json.dumps({'frame_id': msg.header.frame_id}) if msg.header.frame_id else None
    if isinstance(msg, Float32):
        return ts_ns, float(msg.data), None
    if isinstance(msg, Bool):
        return ts_ns, 1.0 if msg.data else 0.0, None
    raise TypeError(f'unhandled msg type for {bridge_topic}')
```

## Detailed Findings — Per Research Question

### Q1: Buffering node placement (new ROS node vs standalone service)

**Recommendation: New ROS node `fc_buffer` in fc_core (option 1a).**

Plan 27-02 (`fc_pwm_driver`) is the freshest example: ~175 lines, single class extending `Node`, registered via `setup.py` `console_scripts`, wired in `fc.launch.py` as a `launch_ros.actions.Node(...)`. Adding `fc_buffer` follows the same shape exactly.

Standalone service was considered for isolation from the 999.25 init-race kills, but:
- A separate service still needs `rclpy.init()` and to join the same DDS domain — *more* surface for the same race, not less.
- SQLite-on-disk already provides crash isolation (the data persists across restarts; only in-flight messages during the crash window are lost — and during that window, the publishers are also dead, so there's nothing to capture).
- Reusing the existing `fc-core.service` systemd unit (with its `ExecStartPre` Tailscale gate) is one fewer thing to deploy and monitor.

One-process-many-subscriptions vs distinct nodes: rclpy is fine with many subscribers in one node. The bridge already has 9 `createSubscription` calls in one node (`mission_control_bridge`); fc_buffer doing the same is unremarkable. [VERIFIED: src/mission-control/bridge/src/index.js:609-751]

### Q2: HTTP server choice in a rclpy process

**Recommendation: stdlib `http.server` in a daemon thread.**

- One endpoint, low RPS (one poll every 30s). Stdlib is more than enough.
- Zero new dependencies (matches D-06 spirit).
- Composes cleanly with `rclpy.spin()`: spin runs on the main thread, http.server runs on a daemon thread. No event-loop integration needed.
- GIL contention concern: real but small. 5Hz × 9 topics = 45 callbacks/sec. A 100ms HTTP serve (`SELECT ... LIMIT 10000` + `wfile.write` of ~800KB JSONL) blocks Python bytecode for that ~100ms — at 45cb/s, that's 4-5 callbacks delayed by up to 100ms each, well within ROS QoS tolerance (KEEP_LAST 10).

`aiohttp`/`flask`/FastAPI: each adds a pip dep with no measurable benefit at this scale. FastAPI in particular wants its own event loop, which fights `rclpy.spin`. Skip.

### Q3: Topic discovery / subscription strategy

**Recommendation: Shared YAML config (`config/buffered_topics.yaml`).**

Three options weighed:
1. **Hardcoded duplicate list with comment** — works today, drifts tomorrow. Phase 999.27 (5 new derived topics) will pile drift on top of Phase 27's 3 new topics already in the bridge.
2. **`get_topic_names_and_types()` + pattern filter** — clever, but requires the publishers to already exist when fc_buffer starts (race), and pattern matching encodes "what counts as a buffered topic" implicitly.
3. **Shared YAML** — explicit, declarative, one file. Bridge and fc_buffer load it. Bridge's existing `ALLOWED_TOPICS` array can derive from this file with `Object.keys` of a map.

The shared-config option also makes the planner's job easier: when 999.27 lands, the change is "add 5 lines to YAML", not "edit two files in two languages."

### Q4: Schema for buffer table + serialization

Schema per CONTEXT D-05 is good as written. Serialization detail confirmed by reading the bridge's existing INSERT path (`insertTelemetry(topic, value)`):

| ROS topic | Bridge `fc.*` topic | Value extraction (from index.js) |
|---|---|---|
| `/fc1/humidity` (RelativeHumidity) | `fc.humidity` | `msg.relative_humidity * 100` |
| `/fc1/temperature` (Temperature) | `fc.temperature` | `msg.temperature` |
| `/fc1/humidity_2` (RelativeHumidity) | `fc.humidity_2` | `msg.relative_humidity * 100` |
| `/fc1/temperature_2` (Temperature) | `fc.temperature_2` | `msg.temperature` |
| `/fc1/co2` (Float32) | `fc.co2` | `msg.data` |
| `/fc1/actuators/humidifier` (Bool) | `fc.humidifier` | `msg.data ? 1 : 0` |
| `/fc1/actuators/humidifier_duty` (Float32) | `fc.humidifier_duty` | `msg.data` (0.0–1.0, do NOT rescale) |

`fc_buffer` must apply the *same* extraction so the buffered `value` exactly matches what the bridge would have written live. The `extra` JSON column is optional v1 — only `RelativeHumidity`/`Temperature` carry `frame_id` (sht30/scd41 provenance, used by Phase 26). Recommend writing it; the bridge's live path doesn't preserve frame_id today, so backfill won't either, but storing it gives future-us the option without a re-buffer.

### Q5: Bridge-side gap detection + replay scheduling

**Recommendation: Periodic poll regardless of perceived state.** Every 30s, ask `since=<last_ingested_ts>`. No DDS state machine, no health probe.

Why simplest wins:
- **CycloneDDS peer-up/down callbacks** in rclnodejs are fragile and not well-documented. Building gap detection on top of them adds a layer that itself can fail.
- **HTTP healthcheck-then-poll** is two requests when one would do. The poll itself IS the health check — if fc1 is unreachable, the request times out and we retry next tick.
- **Polling regardless** means the system self-heals from bridge restarts, missed callbacks, partial Timescale failures, and any other obscure case. The cost of a 30s poll that returns "0 new rows" is one HTTP request + one fast indexed query — negligible.
- During steady-state (no outage), every poll returns ~0 rows because the bridge already inserted them live via DDS, AND the `(topic, time_ns) > last_ingested_ts` filter advances on every successful insert.

**Subtle:** during steady-state the bridge's `last_ingested_ts` advances via *live* inserts, not via *backfill*. So `last_ingested_ts` should be updated by the live `insertTelemetry()` path too — set it to `max(last_ingested_ts, msg.header.stamp_ns)` on every successful live insert. Otherwise the very first post-restart poll re-fetches the entire 24h buffer.

### Q6: Timestamp source-of-truth

**The bridge's existing `insertTelemetry()` writes `new Date()` (NOW), not `msg.header.stamp`.** Verified at `src/mission-control/bridge/src/index.js:587`:
```javascript
'INSERT INTO telemetry (time, topic, value) VALUES ($1, $2, $3)',
[new Date(), topic, value]
```

This is fine for live (latency is tiny) but **wrong for backfill**. The plan must:
1. Change `insertTelemetry(topic, value)` → `insertTelemetry(topic, value, timestampMs = Date.now())`.
2. Backfill always passes the original `time_ns / 1_000_000`.
3. (Optional, recommended) Live path passes `msg.header.stamp.sec * 1000 + msg.header.stamp.nanosec / 1e6` for `RelativeHumidity`/`Temperature`. `Float32`/`Bool` don't carry headers, keep `Date.now()` for those.

`rclpy` (Pi side) exposes `msg.header.stamp.sec` (int) and `msg.header.stamp.nanosec` (int) for messages with a Header. `fc_sensors._publish_temp` and `_publish_humidity` set the stamp explicitly (verified, fc_sensors.py:159, 168). `fc_controller._publish_duty` does NOT set a header (Float32 has no header) — that's fine; `fc_buffer` falls back to its own receive-time, accepting ~ms latency.

### Q7: Backfill conflict policy in Timescale

**Already covered as Pitfall 1 — UNIQUE constraint missing.** Migration is required.

Confirmed against `mushy-timescale-1` 2026-05-02:
```
Indexes:
    "idx_telemetry_topic_time" btree (topic, "time" DESC)
    "telemetry_time_idx" btree ("time" DESC)
```
No PRIMARY KEY, no UNIQUE. Migration: `ALTER TABLE telemetry ADD CONSTRAINT telemetry_topic_time_unique UNIQUE (topic, time);`

TimescaleDB hypertable rule: any UNIQUE/PRIMARY KEY constraint must include the partitioning column (`time`). The proposed `(topic, time)` satisfies this. [CITED: docs.timescale.com — about constraints on hypertables]

Pre-flight dedupe required. The query: `SELECT topic, time, COUNT(*) FROM telemetry GROUP BY 1,2 HAVING COUNT(*) > 1 LIMIT 5;`. If empty, migration is safe. If not, a one-time `DELETE` keeping only the lowest `ctid` per group is the standard fix.

### Q8: fc1 disk + memory budget

Steady-state estimate:
- 9 buffered topics, 5Hz nominal (humidity/temp at 0.5Hz, control/PID at 5Hz; bias high)
- ~45 rows/sec × 86400s = **~3.9M rows in 24h**
- Per row: `topic` (~30 bytes) + `time_ns` (8 bytes) + `value` (8 bytes) + `extra` (~20 bytes typical, mostly NULL) + SQLite overhead (~30 bytes) ≈ **~100 bytes/row**
- **Steady-state DB size: ~390 MB**
- WAL file: a few MB at most under modest write rate; checkpoint absorbs

Pi 4 has 4GB RAM and (per ROADMAP context) plenty of SD/SSD. 400MB is unremarkable.

If the steady-state proves higher than expected, the dial is `retention_seconds` (drop from 86400 → 43200 = 12h, halves disk).

### Q9: Integration with 999.25 (init race)

**Acceptable for v1 — covered as Pitfall 3.** Net data loss vs status quo: zero, because publishers and buffer both die in the same crash window.

If we later want to fix this, options are (a) split fc_buffer into its own systemd unit (then it survives fc-core restarts but adds a second DDS-init point — likely not net-positive), or (b) wait for 999.25 to fix the race itself and let fc_buffer benefit naturally. Recommend the latter.

### Q10: Integration with 999.18 (sensor "last fresh") and alerter

**Verified: alerter consumes via WebSocket, NOT Timescale.** From `src/agents/alerter/src/bridge-client.js:41-50`:
```javascript
ws = new WebSocket(wsUrl);
ws.on('open', ...);
ws.on('message', (data) => { ... }); // dispatches to state machine
```

They are never broadcast on the WS. **The alerter cannot see backfilled points** — neither for "last fresh" timestamps (it tracks `lastSeenMs` from live WS arrivals) nor for re-firing alerts. **The CONTEXT discretion concern about "M minutes old" is therefore not a problem to solve in this phase.** Flag for the planner: the only alerter-side change is *zero*.

The 999.18 concern (alerter's "Last fresh" lies after alerter restart) is real but is its OWN phase. This phase does not improve and does not worsen it.

## Risks & Landmines (synthesized for the planner)

1. **Schema migration on a hypertable with potential dupes (HIGH).** Plan must include: pre-flight dupe check, dedupe step (if needed), then constraint addition, all idempotent. If this skips, every backfill insert raises and silently drops.
2. **Live `insertTelemetry` writes NOW, not stamp (MEDIUM).** Backfill correctness depends on parameterized timestamp. Easy to miss when adding the `buffer-replay.js` consumer.
3. **last_ingested_ns must advance on live inserts too (MEDIUM).** Otherwise bridge restart → re-fetch 24h. Cheap, but wastes bandwidth and IO.
4. **HTTP request without timeout (MEDIUM).** During the very outage we're solving for, naive `http.request` hangs forever. Always set timeout.
5. **YAML config drift between bridge and fc_buffer (LOW once shared file lands).** Paid by future phases adding new topics; the YAML pattern eliminates this.
6. **WAL sidecar files need directory write perms (LOW).** systemd / deploy script must `chown` the parent dir.
7. **GIL contention from a busy HTTP server (LOW).** At 30s polling cadence, no real risk; documented as a knob if it shows up.
