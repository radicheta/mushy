## Problem

Phase 54.1 built the strain double-check loop but only the REPLY half is wired
into the live path. 54.1-03's own "Out of scope" note says it plainly:

> The DETECTION step that SETS `strain_unknown_pending_confirm` on a live draft
> -- that is the extraction/pipeline integration, handled where drafts are first
> persisted. This plan covers the reply side.

That detection step was never built. Verified 2026-05-30:
- `extraction/pipeline.js` has **zero** strain references.
- No live caller of a "collect unknown strains -> dispatch ask-back" step.
- So a live capture with an unknown code flows straight to commit ->
  `upsertFungiAsset(fungiTypeName:'PB2')` -> `fungi_type_not_found` ->
  `partial_commit_failed`.

This is exactly what killed the 2026-05-30 inoc session: draft `cc3944fd` was
confirmed YES at 20:26, then `commit_failed` x3. PB2 was in the notebook but
not the curated set, and nothing asked "is PB2 a new strain?" before committing.

## The reframe (2026-06-01 discuss session)

The original CONTEXT carried four open questions and was leaning toward a NEW
timescale `strain_codes` table to remember confirmed-new codes. Santi pushed
back: **"too many sources of truth."** He was right -- three lists were
competing to define "what strains exist":

1. `strains.yaml` (image-baked) -> `config.strains` (the resolver's match set)
2. farmOS `fungi_type` taxonomy (what mint-on-confirm actually writes)
3. (proposed) a timescale `strain_codes` table

Old decision #1 ("match the curated set, NOT live farmOS terms") is what FORCED
source #3 to exist: if you refuse to trust farmOS, a minted term never makes the
resolver aware of the code, so you need yet another place to write the
confirmation. Self-inflicted complexity.

**Collapse (locked with Santi): farmOS taxonomy is THE single source of truth
for strain existence.** This reverses old decision #1. The code already exists:
`getFungiTypeUuid(client, 'PB2')` (`fungi-type-cache.js:35`) is a cheap per-code
existence check (`filter[name][value]=PB2`).

- **Resolve** = ask farmOS "is this code a `fungi_type`?" -> clean not-found ⇒
  ask the farmer.
- **Mint on YES** = upsert the term via `ensureFungiTypeUuid(client, code,
  {create:true})` (an idempotent get-or-create -- already built, already wired
  through the `createMissingFungiType`/`strain_confirm_approved` marker) and
  commit the draft. The NEXT capture sees it automatically.
- **No new table. STRAIN-07 dissolves.**

`strains.yaml` does NOT disappear -- it keeps its ONE real job: the **extraction
vocab prior** (extractor regex + Haiku gate classifier read `config.strains` to
bias toward expected codes -- see `config.js:122-126`). A stale prior just means
weaker extraction hints; it can NEVER cause a wrong commit. One list, one job.

- `confirm/outbound-confirm.js:283` -- `send_strain_ask_back` dispatch case

- `receive-loop.js:305` -- reply intercept on
  `needs_review_reason === 'strain_unknown_pending_confirm'`:
  YES -> set `strain_confirm_approved` marker -> confirm (commit-watchdog passes

The whole back half works. **Only the trigger is missing.**

## Decisions locked

1. **farmOS taxonomy = single source of truth for strain existence**
   (reverses old "curated set, not live terms"). Resolver existence-checks via
   `getFungiTypeUuid`. `strains.yaml`/`config.strains` demoted to extraction
   vocab prior only.
2. **Gate ONLY on a clean `fungi_type_not_found`.** Infra/HTTP errors or
   `fungi_type_taxonomy_missing` must NOT trigger a farmer ask (the farmer can't
   fix an outage) -- they pass through to the existing commit-time handling.
   Mirrors `ensureFungiTypeUuid`'s own "only honest not-found is actionable" rule.
3. **On YES: just push.** Upsert the term (existing
   `ensureFungiTypeUuid{create:true}` path) + commit the draft. No ceremony,
   no new persistence layer.
4. **Detection insert point = `pipeline.js`**, modeled on the
   `send_starting_seq_askback` short-circuit. NOT the commit-watchdog (the
   ask-back should pre-empt the confirm-preview, not race a commit).
5. **Batched, multi-code aware.** Detection walks ALL codes on the draft
   (top-level `species_code` AND per-group `groups[].species.value` for
   `seeding_session`), collects the DISTINCT unknowns, and sends ONE ask-back
   listing them -- not N pings ([[project_inoc_shape_multi_parent_batch]]).
6. **No blind mint, no silent fail** (carried from 54.1): an unknown code never
   reaches commit without a farmer decision; no-reply leaves the draft held.
7. **Reuse the shipped `renderStrainAskBack` copy** unless deliberately re-toned.

## Open for research / planning (NOT user gray areas -- builder/verify items)

### R1 -- Gate ordering vs `starting_seq` + the SEQ-reply re-entry
A `seeding_session` can need BOTH the `starting_seq` ask AND strain confirm. The
strain reply path (`receive-loop`) currently confirms+commits DIRECTLY, so if
strain detection runs BEFORE `starting_seq` is resolved, a YES could commit a
draft that never got its SEQ. The real 2026-05-30 failure suggests the draft
reaches confirm (SEQ already resolved) and only dies at commit -- so detection
likely belongs at/just-before the confirm-preview dispatch (after `starting_seq`),
NOT as the outermost gate. RESEARCH MUST VERIFY: how does the farmer's
`starting_seq` reply re-enter the pipeline (re-run vs direct-confirm)? That
determines the safe insertion point. Goal: a draft needing both is never
committed missing either.

### R2 -- Multi-group CORRECTION remap
Detection walks per-group; a YES upserts every distinct unknown (fine for
multi-group). But the CORRECTION path (`receive-loop.js:330`) rewrites only a
single top-level `draft_json.species_code`. For a multi-group draft where the
farmer corrects one group's code, that's a gap. PLAN: size per-group remap, or
explicitly scope to single-code corrections with a logged limitation. (YES-path
multi-group works as-is; this is correction-only.)

## Success criteria

- A live capture with an unknown strain code is HELD with
  `strain_unknown_pending_confirm` and the farmer receives the ask-back -- it
  does NOT proceed to a failing commit.
- Existence is checked against farmOS (`getFungiTypeUuid`), gated only on a clean
  not-found; an infra error does NOT ask the farmer.
- Farmer YES -> term upserted in farmOS + draft commits; correction -> remap to
  an existing code, no mint; no reply -> draft stays held (no auto-commit, no
  silent fail).
- A confirmed-new code is known to the resolver on the NEXT capture WITHOUT any
  new persistence layer (it's a farmOS term now).
- Multi-group inoc draft with unknown codes triggers ONE batched ask listing all
  distinct unknowns.
- A `seeding_session` needing both `starting_seq` and strain-confirm commits with
  BOTH resolved (no skip) -- proven by the wiring/integration test.
- A source-level / startup-wiring test proves the detection step is reachable
  from the live capture path (not just unit-green in isolation)
  ([[feedback_unit_tests_dont_catch_wiring]]).
