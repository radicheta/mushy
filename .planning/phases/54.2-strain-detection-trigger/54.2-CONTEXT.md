# Phase 54.2 Context: Strain-detection trigger (live unknown-strain ask-back wiring)

**Status:** Ready to plan
**Created:** 2026-05-30
**Type:** Correctness / wiring (extraction -> farmer confirm -> farmOS taxonomy)
**Follows:** Phase 54.1 (strain-confirm-before-mint, shipped 2026-05-25)

## Problem

Phase 54.1 built the strain double-check loop but only the REPLY half is wired
into the live path. 54.1-03's own "Out of scope" note says it plainly:

> The DETECTION step that SETS `strain_unknown_pending_confirm` on a live draft
> -- that is the extraction/pipeline integration, handled where drafts are first
> persisted. This plan covers the reply side.

That detection step was never built. Verified 2026-05-30:
- `extraction/pipeline.js` has **zero** strain references.
- No live caller of a "collect unknown strains -> dispatch ask-back" step.
- So a live capture with an unknown code flows straight to commit ->
  `upsertFungiAsset(fungiTypeName:'PB2')` -> `fungi_type_not_found` ->
  `partial_commit_failed`.

This is exactly what killed the 2026-05-30 inoc session: draft `cc3944fd` was
confirmed YES at 20:26, then `commit_failed` x3. PB2 was in the notebook but
not the curated set, and nothing asked "is PB2 a new strain?" before committing.

## What ALREADY EXISTS (do not rebuild)

- `farmos/strain-resolver.js` -- `resolveStrain(code, curatedSet)` (exact match,
  uppercase+trim, no fuzzy) + `nearestKnown(code, set)` (display-only suggestion).
- `confirm/strain-ask-back.js` -- `renderStrainAskBack(seenCode, nearest)`
  (the "Saw 'PB2' -- not in the active list. New strain?" message) +
  `parseStrainAskBackReply(text)` (confirm_new | correction | unknown).
- `confirm/outbound-confirm.js:283` -- `send_strain_ask_back` dispatch case
  (WIRED, routes to the draft reply target). Takes `{seenCode, nearest}` extras.
- `receive-loop.js:307` -- reply intercept on
  `needs_review_reason === 'strain_unknown_pending_confirm'`:
  YES -> set `strain_confirm_approved` marker -> confirm (commit-watchdog then
  passes `createMissingFungiType=true`); correction -> validate vs curated set,
  rewrite `draft_json.species_code`, confirm WITHOUT mint marker.
- `farmos/assets.js:86` + `fungi-type-cache.js` --
  `ensureFungiTypeUuid(client, name, {create: createMissingFungiType})` mints
  the term on approved commit.

The whole back half (ask -> reply -> mint/remap) works. **Only the trigger is
missing.**

## The gap to close

Insert a detection step in the live extraction/persist path that:
1. After extraction produces a draft, runs `resolveStrain` over each species
   code against `config.strains`.
2. If any are unknown: hold the draft as `strain_unknown_pending_confirm` and
   dispatch `send_strain_ask_back` (the receive-loop reply side then takes over).

## Decisions locked (carried from 54.1, re-affirmed 2026-05-30 with Santi)

1. Detection = EXACT match vs the curated active set, NOT live farmOS terms
   (live terms may include un-deletable pollution). No fuzzy auto-resolve.
2. No blind mint, no silent fail: an unknown code never reaches commit without a
   farmer decision.
3. Batched double-check: one ask-back message per draft listing all its unknown
   codes, not N separate pings ([[project_strain_confirm_before_mint]] +
   [[project_inoc_shape_multi_parent_batch]]).
4. The farmer-facing phrasing is the existing `renderStrainAskBack` ("Saw 'PB2'
   -- not in the active list. New strain?"). Santi's example ("Hey, saw PB2 in
   the inoc log today! Is this a new strain code?") is the same intent; reuse the
   shipped renderer unless we deliberately re-tone it.

## Open design questions (resolve in discuss/plan)

### Q1 -- Detection insert point
Where does detection run? Candidates:
- (a) `pipeline.js` right after the extractor returns, before persisting the
  draft / before the normal confirm-preview dispatch.
- (b) the commit-watchdog, as a pre-commit gate.
Leaning (a): the ask-back should replace the normal confirm-preview, not race a
commit. Multi-group inoc drafts (`seeding_session`) have codes per group --
detection must walk all groups, collect the distinct unknowns.

### Q2 -- Where do farmer-confirmed-new codes persist? (STRAIN-07)
`tenants/mossrock/strains.yaml` is **baked into the alerter image and NOT
mounted** (container mounts are only `/data/signal-capture` + `/opt/scripts/
signal`). So a YES on "PB2 new strain?" mints the farmOS term, but the curated
set the resolver reads does NOT gain PB2 -- the next PB2 capture asks again.
Options:
- (a) DB table (e.g. `strain_codes` in timescale) that the resolver reads as a
  UNION with the YAML seed. Survives redeploy; runtime-mutable. Most robust.
- (b) `alerter_globals`-style runtime state (already a pattern here).
- (c) Accept "ask once per redeploy" + periodically fold confirmed codes back
  into strains.yaml by hand. Cheapest, leaks friction.
Recommend (a). Needs: a small DAO + the resolver/config reading the union.
NOTE: this also retroactively fixes "PB2" specifically -- once PB2 is in the
store (or YAML), the resolver stops flagging it.

### Q3 -- Multi-code drafts & the seeding_session shape
A `seeding_session` draft has N groups each with a `species`. The 2026-05-30
draft had `species_code` at top level in some paths but per-group in others.
Detection must read the right field(s). receive-loop's correction path writes
`draft_json.species_code` (top-level) -- confirm the seeding_session shape uses
that, or extend to per-group remap. (The shipped reply handler may only handle a
single top-level code; multi-group remap may be a gap to size.)

### Q4 -- Interaction with the existing confirm-preview
A normal draft sends an extraction-preview ask ("YES to commit"). If it ALSO has
an unknown strain, which message wins / what's the order? Likely: strain
ask-back FIRST (gate), then normal confirm. Define the state sequence so the
farmer isn't asked two overlapping questions.

## Success criteria

- A live capture with an unknown strain code is HELD with
  `strain_unknown_pending_confirm` and the farmer receives the ask-back -- it
  does NOT proceed to a failing commit.
- Farmer YES -> term minted + draft commits; correction -> remap to curated code,
  no mint; no reply -> draft stays held (no auto-commit, no silent fail).
- A confirmed-new code is known to the resolver on the NEXT capture (STRAIN-07).
- Multi-group inoc draft with an unknown code triggers ONE batched ask listing
  all unknowns.
- A source-level / startup-wiring test proves the detection step is reachable
  from the live capture path (not just unit-green in isolation).
