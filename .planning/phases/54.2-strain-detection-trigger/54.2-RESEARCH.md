## Summary

The entire strain double-check back-half shipped in Phase 54.1 and is verified live-wired:
`renderStrainAskBack`/`parseStrainAskBackReply` (strain-ask-back.js), the `send_strain_ask_back`
dispatch case (outbound-confirm.js:283), the receive-loop reply intercept on
`needs_review_reason==='strain_unknown_pending_confirm'` (receive-loop.js:305), and the
mint-on-YES authorization (commit-watchdog.js:118 ORs `strain_confirm_approved` into
`createMissingFungiType`). **Only the detection trigger is missing** -- the step in the live
extraction path that walks a new draft's strain codes, checks each against farmOS, holds the
draft, and emits ONE batched ask-back. `pipeline.js` has zero strain references today
[VERIFIED: grep, CONTEXT.md:19].

Research nails down five load-bearing facts. (1) **The gate belongs in `pipeline.js`'s
`enqueue`, on the single-draft path, just before the `send_starting_seq_askback`
short-circuit at :610** -- and it interacts cleanly with `starting_seq` because that gate
RETURNS EARLY before reaching the new strain gate, so a `seeding_session` needing both resolves
SEQ first and only hits strain-detection on the next pipeline pass (R1, verified below).
(2) **The pipeline has no farmOS client today** -- `createExtractionPipeline` (index.js:161)
is constructed without one; `farmosClient` is built later at index.js:331, scoped inside the
`if (credentials)` block. This is the central wiring task: construct `farmosClient` earlier and
inject it. (3) `getFungiTypeUuid` returns a precise discriminated contract -- gate ONLY on
`reason==='fungi_type_not_found'`. (4) `seeding_session` has NO top-level `species_code`; codes
live ONLY at `groups[].species.value` -- which means the existing single-field correction remap
(receive-loop.js:330) is structurally inapplicable to multi-group sessions (R2, decisive
finding below). (5) A source-level wiring guard (the Phase 54.1 precedent at
startup-wiring.test.js:126) is the right STRAIN-08 shape.

**Primary recommendation:** Inject a `farmosClient` into `createExtractionPipeline`; add a
`collectUnknownStrains(draft)` walk + a strain-detection short-circuit in `enqueue` modeled
byte-for-byte on the `send_starting_seq_askback` block (pipeline.js:610-676), placed AFTER it
so SEQ resolves first; gate strictly on `fungi_type_not_found`; for R2, scope corrections to
single-code drafts with a logged limitation (multi-group YES already works; multi-group
correction is a documented gap, not this phase's job).

## R1 (RESOLVED): Gate ordering vs starting_seq + SEQ-reply re-entry

**The question:** A `seeding_session` can need BOTH the `starting_seq` ask AND strain-confirm.
The strain reply path confirms+commits DIRECTLY (receive-loop.js:314). If strain detection runs
BEFORE `starting_seq` is resolved, a YES could commit a draft that never got its SEQ.

**Traced control flow (HIGH confidence -- read every line):**

1. **`enqueue` (pipeline.js:289)** processes a fresh capture. The `starting_seq` short-circuit
   sits at **pipeline.js:610**: when `draft.type==='seeding_session' && draft.needs_input==='starting_seq'`,
   it persists `AWAITING_FARMER` with a `farmer_facing_preview`, dispatches
   `send_starting_seq_askback`, and **`return`s at :669 BEFORE the generic transition** (and
   before any code below it). [VERIFIED: pipeline.js:610-676]

2. **The SEQ reply does NOT re-run `enqueue`.** `handleStartingSeqReply` (pipeline.js:792) is a
   SEPARATE exported function. It re-loads the draft, mints `child_block_names` from the farmer's
   N, clears `needs_input`, persists `AWAITING_FARMER`, and dispatches
   `send_seeding_session_filled_preview` -- it does NOT call `enqueue` and does NOT re-run
   extraction. [VERIFIED: pipeline.js:792-915]

3. **CRITICAL CAVEAT -- `handleStartingSeqReply` is currently UNWIRED in the live receive path.**
   grep across `receive-loop.js`, `capture.js`, and `src/confirm/*.js` for
   `handleStartingSeqReply` / `needs_input` / `starting_seq` / `send_seeding_session_filled`
   returns **zero non-test hits** [VERIFIED: grep]. It is only exercised by unit tests
   (pipeline.test.js) and integration tests. The working branch is literally named
   `fix/inoc-starting-seq-dispatch`, and the breadcrumbs (2026-05-30) confirm the
   `send_starting_seq_askback` DISPATCH case was only just added (`eb8332b`). **The SEQ-reply
   re-entry wiring is itself incomplete on this branch.** The planner must treat the exact
   SEQ-reply routing as not-yet-pinned and design the strain gate so it is correct regardless of
   whether the SEQ reply (a) re-runs `enqueue` or (b) calls `handleStartingSeqReply` directly.

**Recommended insertion point (resolves R1 safely under both re-entry shapes):**

Place the strain-detection short-circuit in `enqueue` **immediately AFTER the
`send_starting_seq_askback` block (after pipeline.js:676), before the generic state-machine
transition at :678.** Rationale:

- A `seeding_session` with `needs_input==='starting_seq'` hits the SEQ gate FIRST and returns
  early -- it never reaches strain-detection on that pass. SEQ is resolved before strain is even
  considered. **A draft needing both is never committed missing SEQ**, because the SEQ ask
  pre-empts everything.
- After SEQ is resolved, the draft's `needs_input` is cleared. **If** the SEQ reply re-runs
  `enqueue` (shape a), the strain gate fires on that pass (no `starting_seq`, so it falls through
  to the new strain block). **If** the SEQ reply calls `handleStartingSeqReply` directly (shape b),
  the strain gate does NOT fire there -- so the planner must ALSO add the
  `collectUnknownStrains` check into `handleStartingSeqReply` just before it dispatches
  `send_seeding_session_filled_preview` (pipeline.js:894), OR move strain-detection to a shared
  helper called from both sites. **The shared-helper approach is strongly recommended** -- one
  `maybeHoldForStrainConfirm(draft, draftId, draftRow, ...)` function called at (i) the
  post-SEQ-gate point in `enqueue` and (ii) just before `handleStartingSeqReply`'s filled-preview
  dispatch. This guarantees the gate fires after SEQ resolution regardless of re-entry shape.

This **confirms CONTEXT's hypothesis**: detection belongs at/just-before the confirm-preview
dispatch (after `starting_seq` is resolved), NOT as the outermost gate. The 2026-05-30 PB2 failure
is consistent: the draft reached confirm (SEQ resolved or N/A for the flat shape) and only died at
commit -- detection placed at confirm-preview-time would have caught it.

**One caveat for the planner:** the batch-mode (`runBatchMode`, pipeline.js:182) and small-N
multi-confirm (pipeline.js:393-514) paths ALSO persist drafts and dispatch confirm prompts, and a
`seeding_session` in a multi-draft capture falls through to `runBatchMode` (pipeline.js:404).
Those paths bypass the single-draft `enqueue` short-circuit entirely. For full coverage the strain
gate (the shared helper) should also run inside `runBatchMode` per-draft before its summary
dispatch -- OR the planner explicitly scopes this phase to the single-draft conversational path
(the path that produced the 2026-05-30 failure) and logs the batch-path gap. **Recommend
single-draft path first (matches the real failure), batch-path as a follow-on** -- but the plan
MUST state the scope decision explicitly so the gap is not silent.

## R2 (DECISIVE FINDING): Multi-group correction remap

**Schema fact (HIGH confidence):** `seeding_session` has **NO top-level `species_code`**. Its
schema is `{type, event_date, groups[], needs_input?, conflicts?, notes?}` where each group
carries `species: Provenanced(z.string().regex(/^[A-Z]{2,4}$/))` -- so strain codes live ONLY at
`groups[].species.value`. [VERIFIED: seeding-session.js:43,74-83]. Top-level `species_code` exists
only on the FLAT shapes (SeedingLog, observation, harvest) where commit-seeding.js:44 reads
`dj.species_code || dj.species || dj.strain || dj.fungi_type`. [VERIFIED: commit-seeding.js:44,
commit-harvest.js:29-31].

**Consequence:** The shipped correction path (receive-loop.js:330) rewrites ONLY
`draft_json.species_code`:
```js
const updatedDraftJson = Object.assign({}, draftRow.draft_json || {}, { species_code: resolved.code });
```
For a `seeding_session`, this writes a top-level `species_code` field that **no commit code ever
reads** -- the per-group `groups[].species.value` stays unchanged, so the correction silently does
nothing for multi-group sessions. This is not merely "a gap"; it is structurally inert for the
canonical multi-parent inoc shape.

**The YES path is fine** (Decision 5): detection collects DISTINCT unknowns across all groups, and
a single YES upserts every distinct unknown via the existing mint authorization -- works for
multi-group because each `groups[].species.value` already carries the real code.

**Options (planner decides):**

| Option | What it requires | Cost | Risk |
|--------|------------------|------|------|
| (a) Per-group remap | A new correction handler that, given a corrected code, finds the group(s) whose `species.value` matches the originally-seen unknown and rewrites them. For an N-unknown batched ask, also needs reply disambiguation ("which code did you mean to correct?"). | Medium-high: new parse surface (which-of-N), new per-group writer, new tests. | Reply ambiguity when >1 unknown; over-scopes this wiring phase. |
| (b) Single-code corrections only + logged limitation | Keep the shipped single-`species_code` remap working for FLAT shapes; for `seeding_session` (or any draft where the seen code is in `groups[]`), the correction path logs `strain_correction_multigroup_unsupported` and re-asks or holds -- never silently no-ops. YES-path multi-group still works. | Low: a guard + a log line + a test asserting no silent no-op. | Farmer must re-drive with a corrected capture for multi-group typos (acceptable; rare). |

**Recommendation: (b).** The 2026-05-30 failure and the common shape both want the YES path (mint
the real code), which already works multi-group. Multi-group CORRECTION (farmer says "that
SHI-looking code in group 2 should be SH2") is genuinely rare and over-scopes a wiring phase.
Ship (b) with an explicit log + a test proving the multi-group correction does NOT silently
no-op (it either re-asks or holds). Per-group remap is a clean follow-on phase if it ever bites.

## How to enumerate ALL species codes on a draft (Decision 5)

The detection walk must handle both draft families:

```js
// Collect distinct strain codes from any draft shape.
function collectStrainCodes(draft) {
  const codes = [];
  if (!draft || typeof draft !== 'object') return codes;
  // Flat shapes (SeedingLog / observation / harvest): top-level fields.
  // Mirror commit precedence (commit-seeding.js:44, commit-harvest.js:29-31).
  const flat = draft.species_code || draft.species || draft.strain || draft.fungi_type;
  if (typeof flat === 'string' && flat.trim()) codes.push(flat.toUpperCase().trim());
  // seeding_session: per-group species.value (the ONLY place codes live here).
  if (Array.isArray(draft.groups)) {
    for (const g of draft.groups) {
      const v = g && g.species && g.species.value;       // [VERIFIED: seeding-session.js:43]
      if (typeof v === 'string' && v.trim()) codes.push(v.toUpperCase().trim());
    }
  }
  return Array.from(new Set(codes)); // DISTINCT (Decision 5: one batched ask)
}
```
Note: provenanced flat shapes nest under `{value}` only inside `groups`. Top-level flat fields are
bare strings (commit-seeding.js reads them bare). Normalize to uppercase+trim to match
`getFungiTypeUuid`'s `filter[name][value]` and the curated-set convention.

## The existence-check contract (Decision 2 -- quote the actual return shape)

`getFungiTypeUuid(client, typeName)` returns a discriminated result [VERIFIED: fungi-type-cache.js:35-51]:

| Return | Meaning | Gate action |
|--------|---------|-------------|
| `{ ok:true, uuid, cached? }` | Term EXISTS in farmOS. | Known -- do NOT ask. |
| `{ ok:false, reason:'fungi_type_not_found', typeName }` | **Clean not-found** (HTTP 200, empty `data[]`). | **THE ONLY actionable case** -- collect this code as an unknown -> ask the farmer. |
| `{ ok:false, reason:'fungi_type_taxonomy_missing' }` | HTTP 404 on the taxonomy endpoint (taxonomy itself absent / infra). | Pass through; do NOT ask (farmer can't fix an outage). |
| `{ ok:false, reason:'http_<status>' }` or `'http_network'` | HTTP error / network failure. | Pass through; do NOT ask. |

**Detection rule (Decision 2):** a code is "unknown -> ask" **iff** `getFungiTypeUuid` returns
`ok:false && reason==='fungi_type_not_found'`. For `ok:true`, skip. For any OTHER `ok:false`
reason, the planner must decide pass-through behavior: **do NOT hold/ask** -- let the draft flow to
the existing commit-time handling (which will retry/fail visibly via the commit-watchdog). This
mirrors `ensureFungiTypeUuid`'s own "only honest not-found is actionable" rule
(fungi-type-cache.js:64).

**Caveat:** `getFungiTypeUuid` has a per-process LRU cache (CACHE_MAX=16). If a code was minted
this process-lifetime, it returns cached `ok:true` -- correct. The dev-pollution terms (next
section) will return `ok:true` and SUPPRESS the ask in dev until cleaned.

## Common Pitfalls

### Pitfall 1: Gating on the wrong `ok:false` reason
**What goes wrong:** Treating any `getFungiTypeUuid` failure as "unknown -> ask" asks the farmer
during a farmOS outage (HTTP error) -- the farmer can't fix it and the draft is stuck.
**How to avoid:** Filter STRICTLY on `reason==='fungi_type_not_found'` (Decision 2). All other
`ok:false` reasons pass through to commit-time handling.
**Warning sign:** Ask-backs firing when farmOS is down; `http_*` / `taxonomy_missing` triggering asks.

### Pitfall 2: Rewriting top-level `species_code` on a seeding_session
**What goes wrong:** A correction writes `draft_json.species_code` on a session draft; no commit
code reads it; the correction silently no-ops (R2). The farmer thinks they fixed a code; the
commit uses the old per-group value.
**How to avoid:** Per R2 recommendation (b): guard the correction path against session/group
shapes; log + re-ask, never silent no-op. Add a test asserting no silent no-op.
**Warning sign:** A test that confirms a session draft after "correction" without checking
`groups[].species.value` actually changed.

### Pitfall 3: Placing the strain gate as the outermost gate (before starting_seq)
**What goes wrong:** A `seeding_session` needing both gets a strain YES that commits a draft with
unresolved SEQ (no child_block_names).
**How to avoid:** Place strain-detection AFTER the SEQ short-circuit (R1). Use a shared helper
called from both `enqueue` (post-SEQ) and `handleStartingSeqReply` (pre-filled-preview) so it
fires after SEQ resolution regardless of re-entry shape.
**Warning sign:** A committed seeding_session with `NEEDS_SEQ` sentinels in child_block_names.

### Pitfall 4: The dispatch-case wiring-bug class ([[feedback_unit_tests_dont_catch_wiring]])
**What goes wrong:** Unit tests inject a fake dispatcher/farmosClient and pass green, but the live
`outbound.js` dispatch switch (the non-confirm dispatcher) lacks the case, or index.js never
injects the client -- exactly the `send_starting_seq_askback` bug fixed in `eb8332b` (2026-05-30)
