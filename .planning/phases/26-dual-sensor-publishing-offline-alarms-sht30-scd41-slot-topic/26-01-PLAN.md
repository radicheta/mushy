<objective>
Refactor fc_sensors.py to publish SCD41 on slot-2 topics (fc1/temperature_2, fc1/humidity_2)
unconditionally and independently of SHT30, while keeping slot-1 silent-fallback behavior
exactly as it is today (D-01). Track per-sensor read timestamps so each slot only publishes
when the backing sensor has produced a fresh value (D-03). Stamp every published message
with `header.frame_id` set to the physical sensor that backed it ('sht30' or 'scd41'),
so downstream consumers (notably fc_controller for sensor_health freshness) can derive
per-physical-sensor liveness without ambiguity. Fix the latent bug where one outer
try/except causes a single-sensor failure to kill both reads.

Extend fc_controller.py's sensor_health publisher (Phase 16 contract) with two new
append-only KeyValue fields — `sht30_fresh` and `scd41_fresh` — driven by per-sensor
staleness against `sensor_stale_timeout`, where SHT30 freshness is derived from
slot-1 arrivals carrying `frame_id='sht30'` and SCD41 freshness is derived from slot-2
arrivals. Republish only on flip (mirror the existing `_warmup_signal_published`
quiet-topic pattern) so Phase 16's TRANSIENT_LOCAL "quiet topic" property is preserved.

Create src/chambers/fc-core/fc_core/test/test_sensors.py with simulation-mode-driven unit
tests that prove D-01/D-02/D-03 behaviors AND frame_id provenance against mocked
self.sht / self.scd handles. No GPIO required.

Purpose: Deliver the data layer that Plan 02 (bridge forwarding) and Plan 03 (alerter
offline alerts) consume. Until this lands, slot-2 topics don't exist on DDS and
sensor_health has no per-physical-sensor freshness signal.

Output: dual-slot publishing on the Pi (verifiable via `ros2 topic list` and
`ros2 topic echo`), per-sensor freshness in sensor_health (verifiable via
`ros2 topic echo /fc1/sensor_health`), frame_id provenance on slot-1/slot-2 messages
(verifiable via `ros2 topic echo` showing the `frame_id` field), and a green pytest
suite under `src/chambers/fc-core/fc_core/test/test_sensors.py`.
