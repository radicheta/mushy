# Phase 27.2: fc-core systemd unit hardening — survive blackout/boot races - Context

**Gathered:** 2026-05-06
**Status:** Ready for planning

<domain>
## Phase Boundary

Close the boot-time fragility exposed by the 2026-05-02 farm power outage so fc-core comes up green on its own after any cold boot or transport bounce, without `reset-failed && start` from a human. Scope is narrow: the systemd unit and a reboot-validation pass. **Not** a refactor of how ROS2 nodes are supervised (that would be the per-node systemd split — separate phase if/when needed).

In scope:
- Verify the IPv4-on-wg0 wait already shipped is correct and is what's actually running on fc1.
- Optional: tighten the systemd dependency graph by adding explicit `After=wg-quick@wg0.service` / `Wants=wg-quick@wg0.service` (defense-in-depth alongside the polling loop, not a replacement).
- Reboot validation: at least one cold reboot and one wg0-down-at-boot scenario, both ending green without manual intervention.
- Update ROADMAP.md text — the SYS-01 description ("currently waits on `ip link show wg0`") is stale; the unit already waits on IPv4.

Out of scope:
- Per-ROS-node systemd splitting (deeper fix for the `ros2 launch` exits-0-on-child-crash trap; current Restart=always + StartLimitBurst is the v1.5.0.1 mitigation).
- Runtime wg0 loss handling (unit-up + endpoint-disappears-mid-grow). Tracked as a possible 999.x if it bites; PID + dwell already keep the chamber stable through transport blips.
- Any 4G / netplan work — fc1 is on home-LAN wifi via wg0; farm-4G return is a future re-promotion of mooted 27.4.

</domain>

<decisions>
## Implementation Decisions

### State of the unit on disk vs fc1 (verified 2026-05-06)
- **D-01:** SYS-01 is already done. Both `scripts/pi-deploy/fc-core.service` and `/etc/systemd/system/fc-core.service` on fc1 (172.16.10.5) wait on `ip -4 addr show wg0 | grep -q "inet "` with a 60-attempt × 1s loop, exit 1 on timeout. ROADMAP.md text claiming "currently waits on `ip link show wg0`" is stale and must be corrected as part of this phase.
- **D-02:** Repo and live unit match byte-for-byte for the relevant blocks. No drift to reconcile, contrary to the usual `feedback_diff_repo_vs_pi_systemd` concern. The phase plan must still re-verify diff at execute time; do not assume identity persists.

### SYS-03 cleanup (explicit wg0 dependency)
- **D-03:** Add `After=wg-quick@wg0.service` and `Wants=wg-quick@wg0.service` to the unit. `wg-quick@wg0.service` exists on fc1, is enabled, and brings up wg0 at boot. Explicit dependency makes the systemd dependency graph honest; the IPv4 polling loop stays as a belt-and-braces safeguard for the edge case where `wg-quick@wg0` is "active (exited)" but the link hasn't actually completed handshake yet.
- **D-04:** Do NOT remove the IPv4 polling loop. systemd `After=`/`Wants=` only sequence units; they don't guarantee the wg interface has an IPv4 address bound when the dependency reports complete. Keep both.

### SYS-04 validation protocol
- **D-05:** Two scenarios, both must end green without `systemctl reset-failed`:
  1. **Cold reboot:** `sudo reboot` on fc1; observe `systemctl status fc-core` reaches `active (running)` and the 5 ROS2 nodes publish on their topics within 2 minutes of boot. Capture `journalctl -u fc-core -b` excerpt as evidence.
  2. **wg0-down-at-boot simulation:** stop and disable `wg-quick@wg0` *before* a reboot, reboot, observe fc-core's ExecStartPre loop times out at 60s and exits 1 (so the unit fails into restart backoff, not into a stuck `rcl_create_node` retry storm), then bring `wg-quick@wg0` back up and confirm fc-core recovers automatically within one StartLimit window (5 retries × 10s ≈ 50s).
- **D-06:** Pass criteria: zero manual intervention in either scenario. Failure = anything that requires the farmer/operator to type a command before the chamber resumes control.
- **D-07:** Run validation while fc1 is still on home-LAN wifi (cheap), not after it returns to the farm. Fresh microSD makes a clean cold boot trivial; this window is the right time.
- **D-08:** Capture before/after timing data: how long from boot to `fc-core` active, and from boot to first telemetry message on `fc1/temperature` reaching the bridge. These become the baseline for any future regression test.

### Carry-over guards (no new work, just preservation)
- **D-09:** SYS-02 already satisfied — `Restart=always` + `RestartSec=10` + `StartLimitIntervalSec=300` + `StartLimitBurst=5` are in the unit. The plan must not regress these. Per `feedback_systemd_restart_ros2_launch.md`, do not change `Restart=` to `on-failure` for ROS2 launch units (`ros2 launch` exits 0 on child crashes).
- **D-10:** No tailscaled references in the unit. The 27.1 transport switch (`b79d9e4`, `24533a9`) already removed dependency on tailscaled; phase plan must not re-introduce it.

### Roadmap cleanup
- **D-11:** Update the Phase 27.2 entry in ROADMAP.md to reflect: SYS-01 done, SYS-03 done after this phase ships, SYS-04 the only outstanding work. Same commit as the unit changes, or a follow-up doc commit.

<code_context>
## Existing Code Insights

### Reusable Assets
- `scripts/pi-deploy/fc-core.service` — Unit already has all the structural mitigations (Restart=always, RestartSec=10, StartLimitIntervalSec=300, StartLimitBurst=5, IPv4-wait ExecStartPre). Phase work is additive (`After=`/`Wants=`) and validation, not a rewrite.
- `scripts/pi-deploy/deploy.sh` (or equivalent) — Standard deployment path. No special handling needed for this phase's changes.
- `fc-update.service` — Boot-time pull from `fc1/prod` branch ensures the unit text catches up after a reboot. Already in `After=`/`Wants=` of fc-core.service; do not perturb this.

### Established Patterns
- **ROS2 systemd pattern:** `Restart=always` + `StartLimitBurst` (NOT `Restart=on-failure`) — established in 27.1 and reinforced by `feedback_systemd_restart_ros2_launch`.
- **fc1 transport binding:** DDS on wg0 only (`cyclonedds-tailscale.xml` despite the filename). Established in 27.1 commits `b79d9e4` and `24533a9`.
- **Pre-flight loops in ExecStartPre:** Bash `for i in $(seq 1 N); do ...; sleep 1; done; exit 1` pattern is the house style for waiting on transient resources (already in use for IPv4-on-wg0). Reuse this if any new pre-flight is added.

### Integration Points
- fc1 only — no bridge, no elder-plops, no farmOS work. Single-node phase.
- The unit talks to `wg-quick@wg0.service` (new explicit dependency) and `fc-update.service` (existing). No changes to either of those units.
- Telemetry consumers (bridge replay-poller, alerter, OpenMCT) see this phase only as "fc-core comes back faster after a reboot" — no schema or topic-shape changes.

</code_context>

<specifics>
## Specific Ideas

- The wg0-down-at-boot scenario is the test that closes the original 2026-05-02 incident class. If only the cold-reboot scenario passes, SYS-04 is **not** complete — the cold reboot only proves the happy path. The original incident *was* the unhappy path (wg link without IPv4 at the moment fc-core started), and the validation must reproduce that class explicitly.
- Capture `journalctl -u fc-core -b -o short-iso` excerpts into the phase directory as evidence files. Two excerpts: one cold-reboot, one wg0-down. Plan should include the file paths so they get committed alongside the phase summary.
- This phase's "ship" event is small enough that it's a candidate for a single combined plan rather than wave-based parallelization. Defer the call to the planner.

</specifics>

<deferred>
## Deferred Ideas

- **Per-ROS-node systemd splitting** — the deeper fix for `ros2 launch` exiting 0 on child crashes. Today's `Restart=always + StartLimitBurst` masks it but doesn't fix it. If fc-core ever gets stuck because one of the 5 nodes silently dies and the launch process doesn't notice, this becomes a real phase. Track as backlog if it bites.
- **Runtime wg0 loss handling** — fc-core is hardened against wg0-not-yet-up at *boot*. Mid-grow loss of wg0 (endpoint reboot on elder-plops, pfSense restart, etc.) would let fc-core keep running on stale DDS state until something else timed it out. PID + dwell + safe-state on the controller side already cover the chamber, but observability would degrade. Not currently a priority — file as a 999.x if observed in the wild.
- **`cyclonedds-tailscale.xml` rename** — cosmetic; filename misleads (binds wg0). Loose end (a) from v1.5.0.1 carryover. Not this phase.
- **USB-SSD migration on fc1** — microSD wear concern from fc_buffer SQLite WAL. Hardware procurement underway, separate work item. Not this phase.

</deferred>
