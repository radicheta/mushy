<action>
In `src/agents/alerter/src/confirm/confirm-db.js`, add three transition helpers. Each takes a `pool` plus a `draftId`. Each runs inside a single transaction with `BEGIN; ... COMMIT;`. Each returns `{ ok: true, rowCount: 0|1 }` (rowCount=0 means idempotent no-op, status was already terminal at the moment of UPDATE) or `{ ok: false, reason }` on a thrown pg error; ROLLBACK on error.

- `confirmDraft(pool, draftId)`: `UPDATE signal_draft SET status='confirmed', confirmed_at=NOW(), terminal_reason='farmer_yes', updated_at=NOW() WHERE id=$1 AND status='awaiting_farmer' RETURNING id;` On rowCount=1, also insert a row into `signal_draft_event` with event='yes' via `appendEvent` (task 3). On rowCount=0, do NOT insert an event row -- the no-op is the no-op.
- `discardDraft(pool, draftId)`: same shape, status='discarded', `discarded_at=NOW()`, terminal_reason='farmer_no', event='no'.
- `expireDraft(pool, draftId, reason)`: same shape, status set based on reason. For `timeout_expired` -> status='expired', `expired_at=NOW()`, terminal_reason=reason, event='expired'. For `superseded_by_newer_draft` -> status='expired', expired_at=NOW(), terminal_reason=reason, event='superseded'. For `edit_cap_exceeded` -> status='needs_review', expired_at=NULL (keep null -- it didn't time out), terminal_reason=reason, event='edit_cap_exceeded'.

Use a client checkout pattern: `const client = await pool.connect(); try { await client.query('BEGIN'); ...; await client.query('COMMIT'); } catch (e) { await client.query('ROLLBACK').catch(()=>{}); return {ok:false, reason:e.message}; } finally { client.release(); }`. The `appendEvent` call inside the transaction uses the same `client`, not the pool.
</action>

- Each issues exactly one `UPDATE ... WHERE status='awaiting_farmer'` (for confirm/discard/timeout_expired/superseded) so a duplicate call returns rowCount=0
- expireDraft with reason='edit_cap_exceeded' sets status='needs_review' (not 'expired') -- verified by a test that asserts the final `status` column value

<action>
Add `appendEvent(client, draftId, event, payload)` to `confirm-db.js`. Signature takes a pg client (NOT the pool) so it can run inside an open transaction. SQL:

```
INSERT INTO signal_draft_event (draft_id, seq, event, payload, created_at)
VALUES ($1, (SELECT COALESCE(MAX(seq), 0) + 1 FROM signal_draft_event WHERE draft_id = $1), $2, $3::jsonb, NOW())
```

Returns `{ ok: true, seq }` (extracted via a RETURNING clause) or `{ ok: false, reason }`. `payload` may be null; cast inside SQL handles that.

Also export a pool-level overload `appendEventViaPool(pool, draftId, event, payload)` for callers that DON'T need to be inside a wrapping transaction (the watchdog's `nudge_sent` event is one such caller). Behavior is identical -- it just opens its own client briefly.

Events recognized for v1.7: `'preview_sent','nudge_sent','yes','no','edit','expired','edit_cap_exceeded','superseded'`. Document the list in a header comment.
</action>
