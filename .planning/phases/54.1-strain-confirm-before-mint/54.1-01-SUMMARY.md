## What Was Built

**`src/farmos/strain-resolver.js`** exports two functions:

- `resolveStrain(code, curatedSet)`: Normalizes input (uppercase+trim), exact-matches against the curated string array. Returns `{ known: true, code }` on match, `{ known: false, code, nearest }` otherwise. Handles null/non-string inputs without throwing.
- `nearestKnown(code, curatedSet)`: Levenshtein minimum-distance neighbor; tie-break by array order. Returns null for empty set. Used for display ("did you mean X?") only -- never auto-remaps.

**`test/farmos/strain-resolver.test.js`** (31 tests, all green):

- Table-driven `it.each` proving all 14 curated codes resolve `known:true` (hermetic; CURATED seeded inline, no config load).
- Cycle-1 variant regression block: LIM->false/LIMA, SHIITAKE->false/SHI, SHITAKE->false/SHI, OYS->false, POY->false.
- KOY documented explicitly as `known:true` (IS in the curated 14; the plan mention of "KOY as POY variant" describes data history, but the resolver correctly honors the curated set).
- Case/whitespace normalization: `'shi'` and `' SHI '` both resolve known:true.
- Edge cases: null/empty/non-string -> known:false, no throw; empty curatedSet -> no nearest field.
- nearestKnown unit coverage: LIM->LIMA, SHIITAKE->SHI, empty->null, tie-break by order.

## Deviations from Plan

**1. [Design Clarification] KOY resolves KNOWN (not UNKNOWN)**

The plan's task description lists "KOY" as a Cycle-1 variant that should resolve UNKNOWN. However, the CURATED set in `tenants/mossrock/strains.yaml` (the source of truth per CONTEXT decision 1) explicitly includes KOY as one of the 14 active codes. Under exact-match semantics, KOY resolves KNOWN:true. The test documents this design decision explicitly with a comment: "KOY IS one of the 14 curated codes; it is not a POY variant in the exact-match model." The CONTEXT's Specific Ideas section notes "KOY (P/K OCR confusion for POY)" -- this describes a data history observation, not a code exclusion. The curated set is the authority.
