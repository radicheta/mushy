<objective>
Wire the controller-side guard. The heater feature is **net-negative without this** — live test 22:02 UTC 2026-05-04 proved PID will spike duty 0→0.85 in response to the synthetic dip. Plan 01's suppress-by-construction prevents the controller from seeing the dip in the first place; this plan adds the belt-and-suspenders guard so that even if a stale poisoned reading is in flight, the controller refuses to act, freezes PID state, and re-engages bumplessly post-window.

This plan also surfaces the heater state into `fc1/sensor_health` DiagnosticStatus (where Phase 26 freshness already lives) so downstream consumers (alerter, bridge, Mission Control) have a single discoverable contract.

Sequencing: Plan 01 must be complete (sensor publishes the Bool topic) before this plan runs. Within this plan, we explicitly handle the **999.32 dependency**: if 999.32 has shipped (filtered derivative), call its reset hook on falling edge. If 999.32 has not shipped, perform inline reset of `self._pid._last_input` and `self._pid._d_term_filtered` (or whatever 999.32-precursor state lives on the vendored simple_pid).
</objective>
